# Loading and Running PTE/PTD in C++

This document answers only two questions: what C++ application compilation and device execution each require, and how to load PTE/PTD generated by ExecuTorch-NPU through the ExecuTorch
`Module`.

## Inputs and Outputs

A C++ application requires at least:

```text
model.pte
ascend.weights.package.ge_aot.ptd
Application input data
```

For how PTE/PTD are generated, see [Model Export](export_en.md). For protocol details, see [Artifact Protocol](protocol_en.md).

## Dependency Boundaries

### C++ Application Build Dependencies

| Dependency | Purpose |
|---|---|
| CMake >= 3.24 | Configuring the application project |
| C++17 compiler | Compiling the application |
| ExecuTorch 1.5.0 full wheel | C++ headers, `libexecutorch.so`, and the CMake package |
| ExecuTorch-NPU wheel SDK | Backend static libraries, state headers, and the CMake interface |
| CANN Toolkit development files | ACL headers and `libascendcl.so` |
| OpenSSL Crypto | Backend Manifest validation |

C++ application compilation does not require Torch, TorchAir, torch_npu, or torch-delegate.

### Device Execution Dependencies

| Dependency | Purpose |
|---|---|
| Compiled application | ExecuTorch invocation entry point |
| `libexecutorch.so` | ExecuTorch Runtime and Module implementation |
| CANN Runtime, NNRT | OM loading and execution |
| Ascend Driver, Firmware | Device operation |
| Target NPU matching the artifacts | Executing offline compilation results |

After the application is compiled, the execution path requires neither Python nor Torch. When deploying
`libexecutorch.so` from the wheel path, keep the corresponding Runtime library or set the correct dynamic library search path.

## Preparing the C++ SDK

Install only the development files in a standalone C++ development environment:

```bash
python -m pip install --no-deps "executorch==1.5.0"
python -m pip install --no-deps /path/to/executorch_npu-*.whl
```

These two commands do not install Torch. Obtain the two SDK root directories:

```bash
export EXECUTORCH_ROOT="$(python -c 'import executorch; print(next(iter(executorch.__path__)))')"
export EXECUTORCH_NPU_SDK="$(python -c 'from executorch_npu import sdk_root; print(sdk_root())')"
source /path/to/cann/set_env.sh
```

## Configuring the CMake Project

Minimal `CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.24)
project(my_runner LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

include("$ENV{EXECUTORCH_NPU_SDK}/cmake/executorch_npu_backend.cmake")

add_executable(my_runner runner.cpp)
target_link_libraries(my_runner PRIVATE executorch_npu::backend)
```

`executorch_npu::backend` transitively provides the ExecuTorch Runtime, OpenSSL, AscendCL, headers, and
the Backend whole-archive registration requirement. Applications should not locate or link the `.a` files in the SDK individually.

Configure and compile:

```bash
cmake -S . -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_PREFIX_PATH="$EXECUTORCH_ROOT" \
  -DASCEND_HOME_PATH="$ASCEND_HOME_PATH"
cmake --build build -j
```

## Loading PTE/PTD

The ExecuTorch 1.5 high-level Module API directly accepts both the PTE and PTD paths:

```cpp
#include <executorch/extension/module/module.h>
#include <executorch/runtime/backend/backend_options_map.h>
#include <executorch/runtime/backend/options.h>
#include <executorch/runtime/platform/runtime.h>

using executorch::extension::module::Module;
using executorch::runtime::BackendOptions;
using executorch::runtime::Error;
using executorch::runtime::LoadBackendOptionsMap;

int main(int argc, char** argv) {
  if (argc != 3) {
    return 2;
  }

  executorch::runtime::runtime_init();

  BackendOptions<2> ascend_options;
  if (ascend_options.set_option("device_id", 0) != Error::Ok ||
      ascend_options.set_option("state_namespace", "my-request") != Error::Ok) {
    return 1;
  }

  LoadBackendOptionsMap backend_options;
  if (backend_options.set_options("AscendBackend", ascend_options.view()) !=
      Error::Ok) {
    return 1;
  }

  Module module(argv[1], argv[2]);
  return module.load(backend_options) == Error::Ok ? 0 : 1;
}
```

After a successful load, obtain input/output metadata via `method_meta("forward")`, construct ExecuTorch
Tensors, and then call `module.forward(...)`. In the repository, `tools/ascend_runner.cpp` is a validation tool with input files and
golden-output comparison, not a general application interface.

## Running the Application

Load the target machine's CANN Runtime environment before execution:

```bash
source /path/to/cann/set_env.sh
./build/my_runner model.pte ascend.weights.package.ge_aot.ptd
```

Notes:

- `device_id` is the ACL Runtime logical device number, which is not necessarily equal to the physical card number shown by `npu-smi`.
- The `acl_soc_name` in the PTE must exactly match the return value of `aclrtGetSocName()`.
- The PTE, PTD, and ExecuTorch-NPU Backend SDK must come from a compatible version combination.
- If PTE/PTD validation fails, the Backend refuses execution at the load stage.

## Stateful Models

The Prefill/Decode state management interface is located in:

```cpp
#include <executorch_npu/state.h>
```

For the API, isolation keys, and state commit semantics, see [C++ Backend SDK: Stateful API](cpp_backend_sdk_en.md#stateful-api).

## Runtime Checks

Check dynamic dependencies:

```bash
ldd build/my_runner
```

It should find `libexecutorch.so`, `libascendcl.so`, OpenSSL, and the system C++ Runtime. For common build
and runtime errors, see [Troubleshooting](troubleshooting_en.md).
