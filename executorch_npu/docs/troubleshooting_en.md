# Troubleshooting

First determine whether the error belongs to the source build, model export, C++ application compilation, or device execution. Do not try to fix
all stages in one environment at the same time.

## Source Build

### ExecuTorch full wheel not installed

Symptom:

```text
ExecuTorch 1.5.0 full wheel with the C++ SDK is not installed
```

Fix:

```bash
python -m pip install --no-deps "executorch==1.5.0"
```

Confirm that the wheel contains:

```text
executorch/include/executorch/runtime/backend/interface.h
executorch/include/executorch/extension/module/module.h
executorch/lib/libexecutorch.so
executorch/lib/cmake/executorch/
```

ExecuTorch 1.0–1.4 is outside the supported range of the current build.

### `Could not find CMAKE_ROOT`

The CMake executable does not match its `share/cmake-*` data directory. Reinstall CMake in the current environment,
and confirm that `command -v cmake` and `cmake --version` point to the same environment.

### CANN header files not found

First run:

```bash
source /path/to/cann/set_env.sh
```

Do not manually splice together multiple CANN installation directories. `ASCEND_HOME_PATH` must point to the Toolkit currently in use.

### `nlohmann/json.hpp` missing

The repository's pinned dependency is located at `third_party/nlohmann_json/include`. Confirm that the repository content is complete; there is no need to set
`NLOHMANN_JSON_INCLUDE_DIR` additionally.

## Model Export

### Wrong Torch wheel installed

Symptoms include missing CUDA dynamic libraries, undefined TorchAir ABI symbols, or being rejected outright by
ExecuTorch-NPU before export.

Confirm:

```bash
python -c 'import torch; print(torch.__version__)'
```

The version must be within 2.9.0–2.13.0 and contain `+cpu`. For reinstallation instructions, see
[Model Export](export_en.md#dependencies-shared-by-both-phases).

### `No module named ge` or `No module named tbe`

This is usually caused by the CANN environment not being loaded, or by overriding the `PYTHONPATH` injected by `set_env.sh` when running the command.

Wrong:

```bash
PYTHONPATH="$TORCH_DELEGATE_ROOT" python export.py
```

Correct:

```bash
export PYTHONPATH="$TORCH_DELEGATE_ROOT:${PYTHONPATH:-}"
```

Long-running tasks, `nohup`, and subprocesses must all inherit the same CANN environment.

### `_torchair.so: undefined symbol`

The TorchAir C++ extension was not compiled with the current Torch. Rebuild a standalone TorchAir for each Torch version,
and do not copy a `_torchair.so` generated by another environment.

### Standalone TorchAir replaced by torch_npu

A standalone TorchAir profile should not install torch_npu. Do not mix standalone TorchAir and
the TorchAir bundled with torch_npu in the same environment.

### `libtorch_delegate_backend.so` not found

Install the whl built from the in-repo `../torch_delegate` (after `bash build.sh` it is located in its
`output/package/`, with the dynamic library inside the package at `torch_delegate/lib/`), or install a released
torch_delegate whl directly; you may also append the source build output directory `../torch_delegate/build/release/csrc`
to `LD_LIBRARY_PATH`. Do not add only the Python source path.

### Import errors such as `guard_or_true`

Other Torch or ExecuTorch source paths have leaked into the environment. Confirm that ExecuTorch 1.5.0 and a
supported CPU Torch are used, and clean up old ExecuTorch paths from `PYTHONPATH`.

### `program.fbs` missing

The current installation is not the ExecuTorch 1.5.0 full wheel, or an old source path is shadowing the wheel. Reinstall the full
wheel; do not manually copy the schema.

### No PTD generated

You must call:

```python
program.write_tensor_data_to_file(output_dir)
```

The PTE and PTD must be produced by the same export and saved as a pair.

### `Disk quota exceeded`

Exporting produces EPAIR files, GE temporary files, OM files, and external weights. Before compiling large models, check the available space in `/tmp` and the artifact
directory, and do not delete `executorch_npu_*` temporary directories still in use by the current process.

The peak temporary weight usage of GE compilation can reach 37 GB (Gemma4 E2B). If you see
`Write data failed, errno: -1` or `Failed to save weight to file`, the file system containing
`EXECUTORCH_NPU_STAGING` is full; point it to a high-capacity disk. Residual
`/tmp/tmp_weight_*` directories left by failures are not cleaned up automatically and must be deleted manually.

### GE `SaveModel` fails across file systems

GE may first generate temporary weights in the current working directory and then move them to the target directory. Place the working directory and the external weight directory on
the same file system, for example both under `/tmp`.

### `ACL set device id failed, return 107001` at compile time

TorchAir's `InitializeGraphEngine` binds the device unconditionally. Set
`EXECUTORCH_NPU_HOST_ONLY=1` to enable Lite export; see
[Model Export](export_en.md#exporting-without-an-npu-device-lite-export).

If the error persists after setting it, check whether `fx2ge_converter.initialize_graph_engine` has been overridden. That module
imports the name directly via `from torchair.core._backend import initialize_graph_engine`, so replacing only the
attribute on `_backend` has no effect.

### `'<' not supported between instances of 'NoneType' and 'int'` when compiling BN/MaxPool without a device

TorchAir converters such as `native_batch_norm_legit_no_training` and `max_pool2d_with_indices`
call `is_arch35()` to select GE op versions, and that function reads the physical device name through
`torch_npu.npu.get_device_name()`. Without a device, torch resolves no device index and returns `None`,
so the following `None < 0` raises `TypeError`; TorchAir only catches `ImportError`, and the exception
propagates straight into the export flow.

With `EXECUTORCH_NPU_HOST_ONLY=1` the Backend already replaces that query with returning `acl_soc_name`; see
[Model Export](export_en.md#exporting-without-an-npu-device-lite-export). If the error persists, confirm that the
conversion happens inside `lower_to_ge_graph()`: the patch is installed by `_load_torch_delegate()`, before
`export_to_epair()`, so calling TorchAir conversion directly without the Backend does not install it.

### plog reports `set ASCEND_RT_VISIBLE_DEVICES[:] error` or `driver error:no valid device`

`ASCEND_RT_VISIBLE_DEVICES=""` is set. The variable has no valid spelling for "zero devices": CANN only
accepts a **non-empty** list of integers within `[0, deviceCount)`, ascending and without duplicates, so the
empty string is treated as malformed (`-1` is out of range as well). This differs from
`CUDA_VISIBLE_DEVICES=""`.

**Fix: unset the variable.** To verify device-less export on a machine that has cards, use a container that
does not map `/dev/davinci*`; see
[Model Export](export_en.md#verifying-device-less-export-on-a-machine-that-has-cards).

Scope of impact:

| Stage | Consequence |
|---|---|
| PT2 export (`DEVICE=cpu`) | No effect |
| host-only compilation (`EXECUTORCH_NPU_HOST_ONLY=1`) | ERROR logs only, compilation continues; a log-keyword-scanning gate still marks it failed |
| Runtime loading and execution of PTE/PTD or OM | **Fails outright**: the visible device count is 0, so `acl.rt.set_device()` returns an error code |

Runtime scripts usually hardcode the device id and raise on a non-zero return, for example all four scripts
under `examples/test_converter/export_llm_model/om_npu_verify/` use `DEV = 0` plus
`ck/check("set_device", acl.rt.set_device(DEV))`. The symptom is that compilation looks fine all the way
through and the failure only appears at runtime.

These ERROR entries come from CANN Runtime and torch_npu; none of the three components in this repository
produces any of them. If **compilation** really aborted, the cause is not these entries but an unstubbed
device query; see the two entries above (`ACL set device id failed, return 107001` and the BN/MaxPool
`TypeError`).

### `TdEpairModelLoaderCreate failed with status=1`

The EPAIR loader requires GE to be initialized, but does not require a device. Under Lite export, initialization should be done by
`ge.offline_compile.build_initialize()`; confirm that `_initialize_ge()` takes the
host-only branch.

### `CANN produced no external weight files`

The host-only `build_initialize` was passed `ge.externalWeightDir`, so external weights were written to the
session workspace. This call must not set that option; GE writes to the partition's
`weight/` directory according to the output path.

### `Offline_compile did not produce expected OM`

Without a device, GE may append a host os/arch suffix to the OM (e.g. `model_linux_aarch64.om`).
The packaging side locates files by the `model*.om` prefix; do not hardcode `.om`.

### `reduce_sum() takes from 3 to 5 positional arguments but 6 were given`

The OPP operator implementation and the TBE Python framework come from different CANN versions. Do not override only `ASCEND_OPP_PATH`;
instead `source` the `set_env.sh` of the same Toolkit. This error only occurs during dynamic Shape compilation.

### `aten.index_put.default ge_converter is not implemented`

The CPU branch of the KV cache used `index_copy_`, for which TorchAir only registers a stub that throws an exception.
The cache should uniformly use `torch_npu.scatter_update_`: this op can also be traced by
`torch.export` on CPU tensors, and produces the same op as the device-side export, introducing no operator replacement or precision differences.

## C++ Application Compilation

### ExecuTorch CMake package not found

Confirm that `CMAKE_PREFIX_PATH` points to the root directory of the installed ExecuTorch package, not the source repository:

```bash
export EXECUTORCH_ROOT="$(python -c 'import executorch; print(next(iter(executorch.__path__)))')"
```

### Still requires `executorch_core` or `extension_module_static`

An old version of the ExecuTorch-NPU CMake files is in use. The current ExecuTorch 1.5 interface uses
`executorch::runtime`, and applications only need to link `executorch_npu::backend`.

### Warnings from ExecuTorch headers amplified by `-Werror`

Use the CMake interface shipped with the wheel SDK. It marks ExecuTorch includes as external SYSTEM
headers while preserving `-Werror` for the user's own source code.

## Device Execution

### Invalid `aclrtSetDevice` parameter

`device_id` is the ACL logical number, which is not necessarily equal to the physical card number shown by `npu-smi`. When only one card is visible,
the logical number is usually 0.

### `DelegateInvalidCompatibility` or error code `0x30`

Common causes:

- The artifact's `acl_soc_name` does not match the device's actual SoC (`aclrtGetSocName()`).
- Version mismatch among PTE/PTD, Backend SDK, or ExecuTorch Runtime.
- Delegate identity validation failure: on the Python side, `to_compile_specs()` outputs only a single
  `ascend_compile_options` JSON CompileSpec, while the Runtime reads the flat
  `method_name`/`delegate_index` keys, obtaining empty strings that can never equal the method in the manifest.
  In this case the log shows `Ascend delegate identity does not match runtime context`,
  and **no artifact can be loaded**. The fix is to make the Runtime parse that JSON
  (`ParseAscendCompileOptions`), rather than rolling back the artifacts.

Re-export using the actual `aclrtGetSocName()`; do not substitute a similar model number.

### PTD missing or validation failed

Confirm that the PTD path is correct, the file has not been modified, and it comes from the same export as the PTE. The Manifest validates keys, logical
lengths, and SHA-256.

### `ldd` shows `not found`

Load the CANN environment before execution, and confirm that the ExecuTorch Runtime libraries are visible:

```bash
source /path/to/cann/set_env.sh
ldd build/my_runner
```

### Output error exceeds the tolerance

Confirm that the input file, reference output, PTE/PTD, SoC, CANN, driver, and firmware all belong to the same validated combination. First complete a single
verification with fixed inputs, then investigate model precision issues.


## Multiple Installation Directories of the Same CANN Version and End-to-End Baseline

Identical directory names or `version.info` do not guarantee identical dynamic libraries. First check
`ASCEND_HOME_PATH` in the project build directory's `CMakeCache.txt` and the
`CANN_ENV_SCRIPT` selected by the export script, then inspect the GE/AscendCL paths actually loaded by the new process.

The installation verified in this development environment is `/mnt/workspace/Ascend/cann-9.1.0`.
In the other installation at `/home/developer/Ascend/cann-9.1.0`, `libgraph_base.so`
lacks the `ge::ATTR_NAME_RTS_OP_IMPL_TYPE` required by its `librts_engine.so`,
which causes the RTS engine to fail to load and manifests as `NetOutput` finding no supported engine.
Choose a complete, matching installation to start new processes, and avoid mixing Python packages and dynamic libraries from different installations.

CANN uses a rename operation when saving external weights. When calling the underlying compilation interface, the staging and output locations must reside on
the same file system; it is recommended to explicitly set `EXECUTORCH_NPU_STAGING` to a working disk with sufficient capacity,
and create that directory in advance. For full exports, prefer the public PTE/PTD export entry points and let the backend
manage its internal staging paths.

When validating a refactor, first let the old version complete export, PTE/PTD loading, and device execution in a fixed environment, then run the new version
with the same model, inputs, and C++ runtime. Compare actual outputs, I/O, and state contracts, covering
host-only/device modes, dynamic range boundaries, cross-method state, request isolation, and resets.
PTE/PTD file digests may vary due to differences in compilation metadata or layout and cannot substitute for numerical comparison.


### Source code changed, but the runner still performs the old validation

The Backend and manifest parser are statically linked into the runner. Rebuilding only the static library or the test program does not update
an existing runner; keeping artifact ABI 1 also does not mean old binaries automatically support newly added state behavior.
After modifying parsing or state logic, rebuild the actually used application in an environment with the correct CANN selected:

```bash
bash examples/scripts/build_runner.sh
```

For example, if the source has removed the single-buffer ABI 2 gate but the run still reports that error, check the actual
runner path, build time, and the error string in the binary, then relink and verify.
