# LLM Engine 基础需求与约束

> 版本：v0.5（草案 / Draft）
> 状态：READ 阶段产物（见 D3），定稿后进入 DESIGN 阶段
> 变更记录见文末

## 目的
设计大语言模型自回归推理使用的 LLM Engine，聚焦顶层推理 pipeline。

**范围界定（本模块负责）：**
- 自回归推理流程编排、Prefill/Decode 两阶段执行
- 队列调度与 batching
- 输入预处理（tokenizer / embedding 查询）
- 后处理（sampler 采样）
- 模型加载、上下文管理
- 对外 C++ API 边界

**范围界定（本模块不负责，由底层运行时封装提供）：**
- KV Cache 管理
- 硬件设备抽象与张量算子执行
- RPC / 服务生命周期 / 多租户鉴权等"服务化"治理

**术语：**
- omc：离线编译模型格式，本模块通过文件路径（图路径 + 权重路径）或已读入的 buffer 加载。
- `PipelineExecutorBase`：`EngineExecutor` 通过 PIMPL 持有的内部组件编排体（impl，约束 #3：抽象基类 + 当前唯一派生 `AutoregressivePipelineExecutor`（自回归）+ `PipelineExecutorFactory` 构造），聚合 `Scheduler` / `PrefillExecutor` / `DecodeExecutor` / `Preprocessor` / `Sampler` / `HistoryPromptManager` 等组件。本 md 中"pipeline"即指 `PipelineExecutorBase` 实例；"Engine 持有 / Pipeline 持有"等表述统一指 `PipelineExecutorBase` 持有对应组件。
- `EngineExecutor`：对外公开类（PIMPL 外壳），用户持有；内部委托 `PipelineExecutorBase`。
- **"Engine 层"**：指 Engine 模块 / 库整体（层概念，如"Engine 层 ModelLoader"指本模块封装的 ModelLoader），与"Engine 持有"（指 PipelineExecutorBase）和 `EngineExecutor`（类）是不同语义，按上下文区分。

**形态与实例模型：**
- 形态为**嵌入式库**（非独立服务）。对外只暴露 C++ API 边界，未来若需服务化由外层 wrapper 实现，对本模块零侵入。
- 用户持有一个 `EngineExecutor` 实例，通过 `Context` 与 `Prompt` 进行上下文管理与推理调用。
- **支持多实例**：调用方可在同一进程内实例化多个 `EngineExecutor`（加载不同模型或不同 session 池）。Engine 不依赖全局单例，资源池归属实例自身。

## 功能点

### 1. 文本 / 多模态 embedding 输入（封装为 `Prompt` 结构）
- **文本输入**：单段 `string`，不引入多轮 chat / messages 列表。
- **embedding 输入**：其它模态（如图像）预计算好的张量；**不包含**绕过 tokenizer 的 token embedding 路径（token embedding 由预处理阶段的 embedding 查询模块产生，见 #7）。
- **混合输入**：同一 Prompt 可同时携带文本与一个或多个模态 embedding。
- **采样参数**：独立为 `SamplingParams` 结构，不放入 Prompt；Prompt 只承载输入内容。
- **纯净设计**：Prompt 不携带 request_id / 优先级 / 回调句柄等调度元数据。
- **避免拷贝**：大张量以 `shared_ptr` / 视图语义传递；Prompt 可移动、可浅拷贝，但内部大对象不深拷贝。
- **字段草案**（仅示意，设计阶段再细化）：
  ```cpp
  struct ModalityEmbedding {
      ModalityTag tag;                       // 模态标识（image / audio / ...）
      std::shared_ptr<Tensor> embedding;     // 共享所有权，避免拷贝
  };
  struct Prompt {
      std::string text;
      std::vector<ModalityEmbedding> embeddings;  // 可空，纯文本时为空
  };
  ```
- **占位符插入方案（已定）**：多模态 embedding 通过文本中的占位符 token 标记位置，在预处理阶段替换（见 #7）。
- **占位符 ↔ embedding 映射机制**：按 `Prompt.embeddings` 数组顺序 ↔ 文本中占位符出现顺序一一对应（不论模态 tag）。即第 i 个 embedding 对应第 i 个占位符。`ModalityEmbedding.tag` 仅作模态标注，不参与匹配。
- **`SamplingParams` 字段草案**（独立结构，不放入 Prompt；散见于 #2 终止条件、#8 采样算法的字段汇齐于此）：
  ```cpp
  struct SamplingParams {
      int max_tokens;                          // 见 #2 (a)
      std::vector<TokenId> stop_token_ids;     // 见 #2 (b)，含 EOS
      std::vector<std::string> stop_strings;   // 见 #2 (b)
      float temperature;                        // 见 #8
      int top_k;                               // 见 #8
      float top_p;                             // 见 #8
  };
  ```

### 2. 自回归推理通路：Prefill / Decode 两阶段
- **两个独立的 `ModelExecutor` 实例**：`PrefillExecutor` 与 `DecodeExecutor` 各自持有并管理一个 omc（Prefill omc / Decode omc），实例独立、便于各自管理生命周期与资源。
- **Executor 职责边界**：前向壳 + KV Cache ringBuffer 光标管理 + load/unload/LoRA 控制委托（per `docs/model_executor/`）。**不**做采样（归 #8 Sampler）、**不**做 KV tensor 内存申请/释放（归底层/`TensorManager`）；KV ringBuffer 光标管理归本模块，符合"目的"中既定边界）。
- **Executor batch 接口**：
  - `PrefillExecutor.forward`：**batch=1**，一次处理一个请求 / 一个 chunk，不与其它 prefill 请求组批
  - `DecodeExecutor.forward`：**batch 维度可 > 1**，一次处理多个 active decode 请求的当前 token（数据并行），上限受模型元信息 `max_batch_size` 约束（见 #4）
  - 两者均为串行接口（C4）：一次 forward 一个 batch，不内建请求级并发；batch 维度属数据并行
- **阶段切换归属**：Prefill → Decode 的切换、Decode 迭代循环的驱动均由 Scheduler 统一管理（与 #3 调度模块衔接），Executor 不自驱跨阶段。
- **自回归循环**：Decode 阶段按 token 级迭代——每步 `DecodeExecutor → logits → Sampler → next token`，next token 回填作为下一步输入，直至终止。
- **Decode 终止条件**（满足任一即停）：
  - (a) 达到 `max_tokens`
  - (b) 命中 stop token（含 EOS）或 stop string
  - (c) 用户主动取消（cancel）
- **Chunked Prefill**：需支持将长 prompt 切块、分多次执行，以控制 TTFT 与单步显存峰值。**切块由 `Preprocessor` 完成**（执行 + 切块策略，基于配置），产出多个 chunk 任务；Scheduler 负责各 chunk 与 Decode batch 的交错调度（策略见 #3 Continuous Batching）。
- **权重共享**：Prefill omc 与 Decode omc 可能引用同一份权重（同模型不同编译版）。底层运行时已支持权重复用机制，Engine 层**不做特殊优化**——直接对两个 Executor 各自调用加载接口即可，由底层去重。

### 3. 队列调度与异步推理接口
- **对外 API（双形态）**：
  - `Generate(Prompt, Context, SamplingParams)`：同步阻塞，返回完整 `Result`。
  - `GenerateAsync(Prompt, Context, SamplingParams, StreamCallback)`：异步提交，立即返回 `RequestHandle`。`StreamCallback` 可选（传空表示非流式）；若提供，每步 Decode 完成后触发，用户在回调中获取该步 token（id + text）。
- **`StreamCallback` 语义**：`using StreamCallback = std::function<void(TokenId, std::string)>`；在 PipelineExecutorBase 后处理每步产出 token 后调用（见 #8）。回调在 PipelineExecutorBase 内部线程触发，用户回调内不应阻塞或调用 Engine 的同步 API。
- **`RequestHandle` 语义**：可查询状态（排队 / Prefill 中 / Decode 中 / 完成 / 已取消 / 失败）、可 cancel、可等待完整 `Result`。`Generate` 等价于 `GenerateAsync`（无回调）+ 阻塞等待。
- **Scheduler 职责边界**：
  - 任务排队（FIFO）
  - 阶段切换（Prefill → Decode 驱动，见 #2）
  - **Continuous Batching**：迭代级动态组批（见下"Continuous Batching 机制"）
  - 各 chunk 任务的交错调度（**切块由 Preprocessor 完成**，见 #7；每块视为独立任务入队）
  - 并发上限控制（decode 池容量 = `max_batch_size`，见下）
- **Continuous Batching 机制（v0.2 起）**：
  - **decode 池**：容量 = 模型元信息 `max_batch_size`（见 #4）。同一时刻最多 N 个请求处于 active decode 状态，组批成一次 `DecodeExecutor.forward`（batch=N）。
  - **请求加入**：新请求 Prefill 完成 → 下一个 decode iteration 加入 decode 池（占用一个空位）。
  - **请求退出**：终止条件（max_tokens / stop / cancel，见 #2）触发 → 当前 iteration 结束后退出 decode 池（释放空位）。
  - **超限处理**：pending decode 请求数 > 空位数时，多余请求在队列中等待，直到有空位释放（continuous batching 核心：请求生命周期跨 iteration，无需等整批完成）。
  - **交错策略（Prefill 与 Decode）**：Prefill 独立（batch=1，不与 Decode 融合 forward）。默认调度策略——**有空位时先处理 Prefill**：若 decode 池有空位（active < max_batch_size）且有 pending prefill 请求，优先执行一个 Prefill（将其带入 decode 池）；否则执行一次 Decode batch iteration。
  - **无 variable padding**：batch 内各请求 KV 相互独立（地址连续但独立管理，不按 batch 内最长补齐）；decode om 图 batch 维固定 = `max_batch_size`，active 未满时 ModelExecutor pad 到 `max_batch_size`（靠 attentionMask 屏蔽 padded 位，per `docs/model_executor/` §1）；prefill om 固定 batch=1 无 padding。
  - **iteration 级组批决策**：Scheduler 每 iteration 决定组批成员（受 max_batch_size 约束）、是否插入 Prefill、batch 内各请求 logits 分发（采样后回填各自历史）。此为 Scheduler 核心职责，不拆出独立 Batcher。
- **并发模型（见 #2 讨论）**：
  - `ModelExecutor` 为**串行接口**，单次前向、不内建请求级并发（C4）。batch 维度属数据并行，非请求级并发。
  - v0.2 起 Decode 阶段支持多 batch（Continuous Batching）；Prefill 仍 batch=1。
  - 并发来源：多实例 EngineExecutor（横向）+ 单实例内 Continuous Batching（纵向）。
- **Cancel 语义（两个粒度）**：
  - **`RequestHandle.cancel`**：取消单个请求。已生成的部分 token **丢弃**，不返回给用户；Handle 进入"已取消"终态。
  - **Context 级 cancel**（通过 `ContextId` 触发）：取消该 Context 上**所有在飞请求**，各对应 RequestHandle 进入"已取消"终态。用于会话整体终止场景。
- **调度模块归属**：Scheduler 是本模块的核心组件，与 PrefillExecutor / DecodeExecutor 协作；Executor 不自驱跨阶段，全部由 Scheduler 编排。

### 4. 模型模块化加载
- **加载时机**：`EngineExecutor` 初始化时一次性加载两个 omc（Prefill omc + Decode omc）。当前版本不支持运行时热加载 / 切换模型。
- **加载来源（仅两种）**：
  - (a) 文件路径：包含 omc 图路径 + weight 路径 + **与 omc 同名的 json 元信息文件路径**
  - (b) 已读入的 buffer：图 buffer + weight buffer + 元信息 buffer
- **`EngineExecutor` 构造签名草案**（对应两种加载来源，各一份 Prefill + Decode）：
  ```cpp
  // 路径加载
  EngineExecutor(OmcPath prefillOmc, WeightPath prefillWeight,
                  OmcPath decodeOmc,  WeightPath decodeWeight,
                  const EngineOptions& options = {});
  // buffer 加载
  EngineExecutor(OmcBuffer prefillOmc, WeightBuffer prefillWeight,
                 OmcBuffer decodeOmc,  WeightBuffer decodeWeight,
                 const EngineOptions& options = {});
  ```
  json 元信息路径由 omc 路径派生（同名 json）；buffer 模式下元信息 buffer 单独传入或并入。`EngineOptions` 聚合可选配置（如 chunk size 默认值、并发上限等，具体字段待设计阶段列）。
- **Engine 层 ModelLoader 职责**（封装加载流程，thin wrapper）：
  1. 解析输入参数（路径或 buffer）
  2. 读取 json 元信息（max batch size / max seq len / dtype / 张量布局等，具体字段待设计阶段列出）
  3. 调用底层 `ModelManager` 完成实际加载
  4. 将加载结果句柄交给对应 `ModelExecutor` 持有
- **底层 `ModelManager`**（底层已封装，Engine 层不重新实现）：
  - 持有加载好的模型实例 + 全部元信息
  - 提供权重复用 / 去重机制（按 #2 既定：Engine 层对两个 Executor 各调一次加载接口即可，由底层去重）
  - 提供释放方法供 Executor 析构时调用
- **加载结果产物**：底层 `ModelManager` 持有的模型实例 + 元信息；`ModelExecutor` 持有对其的引用 / 句柄。
- **错误处理**：使用 **`Status`（非异常）**。加载失败（文件不存在 / buffer 损坏 / 版本不匹配 / json 解析失败等）通过 `Status` 返回（粗粒度码，详情靠日志 C11），贯穿整个 Engine 的 API 风格（见 C2）。
- **资源释放**：RAII 风格——`ModelExecutor` 析构时调用底层 `ModelManager` 的释放方法。不提供显式 `unload` 接口。

### 5. 上下文（Context）管理
- **所有权**：Context 由**用户持有**。EngineExecutor 提供接口：
  - `CreateContext`：创建 Context，返回 `ContextId` + Context 句柄
  - `DestroyContext`：销毁 Context（释放对应 HistoryPromptManager、底层 KV 句柄等）
  - `ConfigureContext(ContextId, ...)`：配置 Context 可配置字段（见下"可配置字段"）
  - `CancelContext(ContextId)`：Context 级 cancel，取消该 Context 上所有在飞请求（见 #3 Cancel 语义）
- **可配置字段（当前版本）**：
  - 用户自定义 metadata（字符串 / 任意 KV）
  - 其余可配置项（如该 Context 的默认 chunk size 覆盖、并发上限覆盖）**待设计阶段列**
- **多轮对话续接**：每轮调用 `Generate` / `GenerateAsync` 时，Prompt **只含本轮新增文本**；已生成的历史 token 由单独的 `HistoryPromptManager` 模块管理（见下）。
- **切换语义**（支持 a + b）：
  - (a) 同一 EngineExecutor 内多个 Context 间切换（多会话复用同一 Engine）
  - (b) Context 在 Prefill / Decode 阶段间传递状态（阶段游标、KV 句柄等）
  - **不支持**跨 Engine 实例迁移 Context
- **Context 只持有引用**：内部状态以引用 / 句柄形式持有，数据本体在底层（KV）或 `PipelineExecutorBase` 内部（HistoryPromptManager）。
- **KV 切换在底层处理**：多会话切换时 KV cache 的换入 / 换出由底层运行时透明处理，Engine 不感知、不参与调度（符合"KV 在底层"边界）。
- **持久化**：当前版本不支持 Context 保存 / 恢复。

**Context 承载内容草案（设计阶段细化）：**

A. 用户可见 / 可配置（public）：
- `ContextId`：标识，用于多会话切换、状态查询、Context 级 cancel（见 #3 Cancel 语义）
- 用户自定义 metadata（可选）

B. `PipelineExecutorBase` 内部状态（Context 持有引用 / 句柄）：
- KV cache 句柄：引用底层管理的 KV
- `HistoryPromptManager` 句柄：引用 `PipelineExecutorBase` 持有的 HistoryPromptManager 实例（按 Context 隔离，见 #9）
- 推理阶段状态：stage（idle / prefilling / decoding / done）、序列游标（已处理 token 位置，用于 chunked prefill 续接）
- 隶属的 EngineExecutor 引用（隐式或显式）

**新增模块：`HistoryPromptManager`**（见功能点 #9，独立功能点 / 模块，被 `PipelineExecutorBase` 持有）

### 6. 对外接口层分离
- **分离机制：PIMPL**。`EngineExecutor` 为具体类，impl 隐藏在 .cpp；public 头文件不暴露任何内部类型。
- **公开类型清单**（出现在 public 头文件）：
  - `EngineExecutor`、`EngineOptions`、`Context`、`ContextId`、`Prompt`、`ModalityEmbedding`、`Tensor`（底层提供、forward declare 于 public 头）、`ModalityTag`、`TokenId`、`SamplingParams`、`RequestHandle`、`Result`、`StreamCallback`、`Status`（状态码 struct，含 `static constexpr` 常量）、`Buffer`、`ModelArtifact`、`ModelArtifactPath`
- **内部类型清单**（不出现在 public 头）：
  - `PipelineExecutorBase`（EngineExecutor 的 PIMPL impl）、`Scheduler`、`ModelExecutor`（`PrefillExecutor` / `DecodeExecutor` 为其两实例）、`Preprocessor`、`HistoryPromptManager`、`Tokenizer`（engine 内部多态模块 `TokenizerBase`+工厂+BPE/SP，C8 v1.2）、`TextEmbedding`（engine 内部 embedding 模块，load+bind）、`Sampler`（engine 内部具体类）；`IModelManager` 为唯一 L2→L3 抽象接口（经链接期 `CreateModelManager()` 工厂创建，见 C8 v0.11）。各模块辅助类型（`ModelHandle` / `ModelMetaInfo` / `ModalityEntry` / `RequestImpl` / `RequestId` / `StepOutput` 等）见 `04-interfaces` 下半。
- **可选 C API 层**（见 `docs/c_api/`）：在 C++ API 之上提供 `extern "C"` 薄封装（opaque handle + POD struct），为跨语言绑定提供 ABI 稳定边界。不替代 C++ API；C API 公开类型为 C 兼容的 POD struct + opaque 指针（`CANN_LMEngine_Executor` / `CANN_LMEngine_Request`）+ 值类型（`CANN_LMEngine_ContextId`）。详见 c_api SPEC/DESIGN v0.1.0。
- **线程模型**：
  - `GenerateAsync`：可多线程并发调用，API 线程安全（请求安全入队）
  - 多 `Context`：允许并发提交（提交层并发，执行层仍串行，见 #2/#3）
  - 同一 `Context`：并发调用**返回错误**（显式暴露问题，避免隐性排队掩盖 bug）
  - `Generate`（同步）：按 `GenerateAsync` 实现 + 阻塞等待达成同步效果；并发行为同 `GenerateAsync`
- **ABI 稳定性**：当前版本不承诺 ABI 稳定，源码级兼容即可。

### 7. 输入预处理流程
- **engine 内部模块（C8 v1.2，由 Engine 自身实现）**：
  - `Tokenizer`（=`TokenizerBase` 多态基类 + `TokenizerFactory` + BPE/SentencePiece 派生自注册，见 `docs/tokenizer/`）：文本 → token id；M-02 经工厂 `unique_ptr<TokenizerBase>` 持有
  - `TextEmbedding`：加载 embedding 表并绑定至模型（per `docs/model_executor/` §4.1.1；tokenId 查表在 om 图内部，非查表产张量）；M-02 按值持有
  - `Sampler`（engine 内部具体类，无多态需求）：logits + 采样参数 → token id；M-02 按值持有
- **独立 `Preprocessor` 模块**协调整条预处理链路（单一职责，Scheduler 只管调度，不串联预处理）。
- **预处理完整链路（Prefill 路径）**：
  ```
  Prompt.text（含占位符 token）──Tokenizer──► token ids ─────┐
                                                               ├─ 拼接 ─► 完整 token id 序列
  HistoryPromptManager 历史 token ids ──────────────────────┘              │
                                                                          ▼
  占位符替换：占位符位置填入对应多模态 embedding ─► 混合序列
  （占位符位置为 embedding 张量；其余位置为 token id，查表在 om 图前向内部）
                                                                          │
                                                                          ▼
  TextEmbedding LoadAndBind（init 期加载表+绑定模型）─► token id 序列 + 多模态占位 ─► 切块（见下）─► Executor（om 图前向内部按 tokenId 查表）
  ```
- **占位符替换**：多模态 embedding 通过文本中的占位符 token 标记位置，在预处理阶段替换为对应模态 embedding（对应 #1 已定方案）。映射按 `Prompt.embeddings` 数组顺序 ↔ 占位符出现顺序（见 #1）。
- **Chunked Prefill 切块归属（已定）**：由 `Preprocessor` 完成切块（执行 + 切块策略，基于配置的块大小），产出多个 chunk 任务交 Scheduler；Scheduler 仅负责各 chunk 与其它任务/Decode 的交错调度。
- **Decode 单步预处理（轻量子集）**：上述链路为 Prefill 输入。Decode 每步只需 `单 token id → 输入张量 → DecodeExecutor`（tokenId 查表在 om 图前向内部），是 Prefill 预处理链路的轻量子集，由 Preprocessor 提供 fast path。

### 8. 后处理流程（采样 + detokenize + stop 检测）
- **Sampler 归属**：engine 内部具体类 `Sampler`（C8 v1.2，无多态需求），`PipelineExecutorBase` 按值持有；无状态、不感知历史。
- **支持算法（基础）**：greedy、top-k、top-p、temperature。
- **不支持**：Beam search、多采样（n > 1）、logprobs 返回、repetition / frequency / presence penalty 等历史相关算法（因 Sampler 暂不感知历史，见下）。
- **Sampler 暂不感知历史**：Sampler 只接收当前步 logits 产出 token id，不读 `HistoryPromptManager`。因此 penalty 类算法不支持，留待后续版本。
- **后处理流程**（由 `PipelineExecutorBase` 控制）：
  ```
  Executor 输出 logits
        │
        ▼
  Sampler 采样 ─► token id
        │
        ├─► PipelineExecutorBase 写入 HistoryPromptManager（见 #9）
        │
        ▼
  Tokenizer detokenize（流式）─► text
        │
        ├─► 触发 StreamCallback（若已注册，见 #3）─► 用户获取该步 token
        │
        ▼
  stop 检测
        ├─► stop token（含 EOS）：token id 级别，Sampler 输出后即比较
        └─► stop string：text 级别，detokenize 后在明文上检测
        │
        ▼
  决定是否终止（见 #2 终止条件）
  ```
- **StreamCallback 触发点**：每步 detokenize 产出 text 后、stop 检测前触发（见 #3 `StreamCallback` 语义）。命中 stop string 时该步 token 是否回调由设计阶段定（倾向：不回调命中 stop 的那步，避免向用户泄露停止标记）。
- **输出形态**：`Result` 同时包含 token id 序列与 text（`PipelineExecutorBase` 控制从 token id 经 Tokenizer 转 text 的流程）。
- **stop string 检测细节（待设计阶段确认）**：流式 detokenize 缓冲策略、命中 stop string 时缓冲区已生成部分的去留策略。


### 9. HistoryPromptManager（历史 token 管理，独立模块）
- **定位**：独立功能点 / 模块，被 `PipelineExecutorBase` 持有（PipelineExecutorBase 是 EngineExecutor 的 PIMPL impl，见术语），按 Context 隔离（每个 Context 对应一个实例）。
- **职责**：管理单个 Context 跨轮次累积的 **token id 历史**，供下一轮 prefill 拼接使用。
- **存储形态**：token id 序列（非文本），避免反复 tokenize 与 tokenizer 非双射损失。
- **写入主体**：`PipelineExecutorBase` 内部写入。每步 Decode 后 Sampler 采样出新 token，由 `PipelineExecutorBase` 写入对应 Context 的历史（用户无感）。
- **读取用途**：下一轮 prefill 时，`PipelineExecutorBase` 从 `HistoryPromptManager` 取历史 token id + 本轮 Prompt 新文本经 tokenizer 切分得到的新 token id → 拼接成完整输入序列。
- **待设计阶段确认**：截断 / 滑动窗口策略、与底层 KV 长度对齐策略。


## 约束

### C1. 模块封装
足够独立且复杂度足够高的模块需单独封装。本模块需独立封装的清单：
- `EngineExecutor`（对外接口层，PIMPL）
- `Scheduler`
- `PrefillExecutor`、`DecodeExecutor`（`ModelExecutor` 的两个实例）
- `Preprocessor`（协调 `TokenizerBase` / `TextEmbedding` / 占位符定位 / 切块；tokenId 查表在 om 图内部）
- `HistoryPromptManager`
- engine 内部模块 `Tokenizer`（`TokenizerBase`+工厂+BPE/SP，经工厂 `unique_ptr` 持有）/ `TextEmbedding`（load+bind，按值）/ `Sampler`（具体类，按值）（C8 v1.2）；L2→L3 注入点 `IModelManager`（经链接期 `CreateModelManager()` 工厂创建 owned MM，后端编译时确定，不另建壳类，见 C8 v0.11）

### C2. 错误处理
**统一使用 `Status`（非异常）**，贯穿全部 public API。`Status` 为 struct，持 `int code`，带一组 `static constexpr` 常量（`SUCCESS=0` / `FAILURE=1` / `INVALID_ARGUMENT=2` / `INVALID_STATE=3` / `NOT_FOUND=4` / `CANCELED=5`）；详细失败原因经日志（C11）输出，状态码仅给粗粒度。值返回型操作签名 `Status Op(..., T* out)`（值经 out 参数返回），无值返回型操作签名 `Status Op(...)`。无 `StatusOr`、无异常。

### C3. 避免拷贝
大对象（张量、buffer、历史 token 序列）一律用 `shared_ptr` / 视图语义传递；可移动、可浅拷贝，禁止内部大对象深拷贝。

### C4. ModelExecutor 串行接口
`ModelExecutor` 为串行接口，单次前向、不内建请求级并发。**batch 维度可 > 1（数据并行，非请求级并发）**——`DecodeExecutor.forward` 一次处理多个 active 请求的当前 token（Continuous Batching，见 #3）。并发来源仅为**多实例**（横向）+ **单实例内 Continuous Batching**（纵向）。

### C5. 边界纪律：Engine 层不感知下层
Engine 层不感知 KV Cache 管理、硬件设备抽象、张量算子执行、设备调度。这些由底层运行时封装提供，Engine 层只调用封装接口。

### C6. 接口分离
PIMPL + 公开/内部类型清单分离（见功能点 #6）。public 头文件不暴露任何内部类型。

### C7. 多实例
不依赖全局单例，支持多实例。资源池归属 `EngineExecutor` 实例自身。

### C8. 下层封装模块
- **L2→L3 注入点**（抽象接口，底层提供实现，01 §7.2 注入点）：`IModelManager`——经链接期自由函数 `CreateModelManager()` 创建 owned `unique_ptr<IModelManager>`（D-12，后端编译时确定）；ModelExecutor::Load 自调工厂创建并持有，pipeline 不感知后端类型。不再经 `shared_ptr` 运行时注入（v0.11 硬切）。
- **engine 内部模块**（C8 v1.2）：`Tokenizer`（多态 `TokenizerBase` + 工厂 + BPE/SP 派生自注册，经工厂 `unique_ptr` 持有，per `docs/tokenizer/`）、`TextEmbedding`（load 表+绑定模型，按值，per `docs/model_executor/` §4.1.1）、`Sampler`（具体类，无多态需求，按值）——由 Engine 自身实现、可从测试数据/工厂桩构造。`TokenizerBase` 有虚函数（多态分派）；`TextEmbedding`/`Sampler` 无多态需求。

### C9. 语言标准
**C++17**。

### C10. 依赖原则
**最小依赖**。仅必要时引入第三方库（如 `nlohmann/json` 用于读 omc 同名 json 元信息，见 #4）。**日志库与测试框架均自研**，不引入 `spdlog` / `GoogleTest` 等。

### C11. 日志
Engine 层需要日志（调度、加载、错误等可观测性），使用**自研轻量 logger**。

### C12. 代码风格
**待定**（开发阶段统一，建议同步写入 `AGENTS.md` 的 lint/format 配置）。
