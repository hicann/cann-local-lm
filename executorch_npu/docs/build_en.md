# Building ExecuTorch-NPU from Source

This document answers only two questions: what the build requires, and how to build the source into a platform wheel containing the Python AOT Backend and
the C++ Backend SDK. For model export, see [Model Export](export_en.md); for C++ application compilation and
device execution, see [Running in C++](runtime_en.md).

## Build Scope

Default command:

```bash
bash build.sh
```

The default build produces:

```text
output/package/executorch_npu-<version>-<python>-<abi>-<platform>.whl
build/release/install/include/executorch_npu/
build/release/install/lib/libexecutorch_npu_backend.a
build/release/install/lib/libexecutorch_npu_manifest.a
```

The default build does not produce a Runner and does not perform model export.

## Build Dependencies

### Tool Dependencies

| Dependency | Requirement | Purpose |
|---|---|---|
| Python | 3.10 or later | Packaging and build checks |
| pip, setuptools, wheel, packaging | Available in the current environment | Generating the wheel |
| CMake | 3.24–3.x | Configuring and compiling C++ targets |
| C++ compiler | C++17; currently validated with GCC 9.4 | Compiling the Backend |
| OpenSSL development package | Provides Crypto | Manifest SHA-256 |
| nlohmann_json | Pinned to 3.11.3 in the repository | Manifest JSON parsing |

### Software Dependencies

| Dependency | Purpose |
|---|---|
| ExecuTorch 1.5.0 full wheel | Backend headers, `libexecutorch.so`, CMake package, and version information |
| CANN Toolkit development files | ACL headers; also provides `libascendcl.so` when linking the Runner/application |

The build does not depend on Torch, torchao, TorchAir, torch_npu, torch-delegate, or an NPU device.
ExecuTorch must be the full wheel; the minimal wheel lacks the required C++ SDK.

## Preparing the Build Environment

We recommend creating a dedicated environment for the source build:

```bash
python3 -m venv /path/to/executorch_npu-build-env
source /path/to/executorch_npu-build-env/bin/activate

python -m pip install --upgrade pip
python -m pip install \
  "setuptools>=68" \
  "wheel>=0.40" \
  "packaging>=23" \
  "cmake>=3.24,<4"
```

The Backend build only consumes the C++ development files from the ExecuTorch wheel, so use:

```bash
python -m pip install --no-deps "executorch==1.5.0"
```

`--no-deps` applies only to this isolated build environment. The model export environment must not copy this command verbatim.

Load the installed CANN environment:

```bash
source /path/to/cann/set_env.sh
```

The software build requires CANN development files but not an actual NPU. `build.sh` uses
`ASCEND_HOME_PATH` to locate CANN, so users do not need to configure header paths one by one.

## Running the Build

```bash
cd /path/to/executorch_npu
bash build.sh
```

Debug build:

```bash
bash build.sh --debug
```

Script execution order:

```text
Check Python, CMake, CANN, and the ExecuTorch full wheel
→ Configure and compile the Backend static libraries
→ Run C++ unit tests
→ Install headers and static libraries to build/<type>/install
→ Package the Python package and C++ SDK into the platform wheel
```

`build.sh` does not create a virtual environment and does not modify dependencies in the current environment.

## Inspecting and Installing Artifacts

Confirm the actual wheel file name:

```bash
ls -1 output/package/executorch_npu-*.whl
```

Install the corresponding wheel into the target environment:

```bash
python -m pip install /path/to/executorch_npu-<version>-<python>-<abi>-<platform>.whl
```

If you only need to extract the C++ SDK without installing the Python export dependencies, you can use the following in an environment where the ExecuTorch 1.5
full wheel is already installed:

```bash
python -m pip install --no-deps /path/to/executorch_npu-*.whl
python -c "from executorch_npu import sdk_root; print(sdk_root())"
```

The `compatibility.json` in the wheel records the ExecuTorch version, commit, CANN,
Python, and compiler actually used by the build. This file is generated by the build process and must not be modified by hand.

## Development Quality Checks

In an environment with the development and example dependencies installed, run from the repository root:

```bash
python -m pip install -e '.[test]'
ruff check python tests examples scripts
ruff format --check python tests examples scripts
python scripts/generate_manifest_schema.py --check
CANN_MANIFEST_TEST_BINARY="$PWD/build/release/executorch_npu_manifest_test" \
    python -m pytest tests/python -q
ctest --test-dir build/release --output-on-failure
```

If torch_npu is installed but you do not want Torch to auto-import device extensions, set
`TORCH_DEVICE_BACKEND_AUTOLOAD=0`. Model tests still explicitly import operator registration on demand;
tests that require an NPU are executed or skipped based on device availability. The CPU eager cache is updated using the PyTorch
reference; CPU/FakeTensor export preserves native NPU operators; the fused GDN tests use
BF16 and a 128-dimensional state head.

This round of quality cleanup referenced three concrete patterns from PyTorch 2.7.1:
Dynamo guarding global state at the compile entry (`torch/_dynamo/convert_frame.py`),
backends explicitly maintaining initialization state (`torch/cuda/__init__.py`), and configuration contexts restoring state on exceptional exit
(`torch/utils/_config_module.py`). ExecuTorch-NPU uses its own synchronization and state management
and does not depend on these private PyTorch implementations.


### Python Style

Consistent with the referenced PyTorch 2.7.1 configuration: 88 columns, double quotes, import grouping, and two blank lines after imports.
`requirements-dev.txt` pins the Ruff version; the check entry points are described above.

- Functions, methods, ordinary variables, and mutable module state use `snake_case`; internal helper functions and internal state are prefixed with `_`.
- Classes use `CapWords`, and constants use `UPPER_CASE`. The upstream Transformers
  `Qwen3_5*` model naming is preserved to keep configurations, checkpoints, and existing interfaces consistent.
- Classes manage state or resources with a clear lifecycle, such as `OfflineCompiler`; stateless transformations and validations use functions.
- Public and module-boundary declarations are typed; exception conversions use explicit exception chaining; test names describe observable behavior.
- The mutable compile lock and session instance are named `compile_lock` and `offline_compiler`, respectively.
