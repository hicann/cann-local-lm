# TorchDelegate CPU/NPU Mixed Scheduling Design (HostCpu Backend)

# Introduction

## Purpose

This document describes the requirements and design of the TorchDelegate CPU/NPU mixed scheduling capability. It addresses one problem:

> When a model contains operators that have no NPU execution path and can only run on CPU, how can they work together with NPU operators in the same GE graph without per-operator host↔device round trips?

## Scope

**Included**:

- Analysis of the current state and verification of key prerequisites
- End-to-end design: IR extension, device ownership resolution, code generation, graph building, GE scheduling and execution, diagnosability
- Changed-file inventory, phased implementation steps, DT design, acceptance criteria, and risk list

**Excluded**:

- Implementation details of GE internal graph optimization
- Operator coverage improvements of the torchair converter
- TorchDelegate's offline OM deployment path
- Training scenarios

## Terms

| Term | Meaning |
|------|---------|
| converter node | A node successfully converted by torchair with `ascend_ir.source == "converter"`; mapped to a GE built-in operator |
| fallback node | A node with `ascend_ir.source == ""`; a GE custom operator is generated by Fallback Codegen, which calls back into the PyTorch Dispatcher at runtime |
| Device-backend custom operator | Registered with `OpBackend::kDevice` (`REG_AUTO_MAPPING_OP`); `Execute` calls the PyTorch `PrivateUse1` (NPU) implementation |
| CPU node / HostCpu custom operator | New in this feature: a node with `ascend_ir.device == "cpu"`; registered with `OpBackend::kHostCPU` (`REG_OP_BACKEND`); `Execute` calls the PyTorch `CPU` implementation |
| `HostCpuExecuteOp` | GE custom operator capability interface; `Execute(gert::HostCpuOpExecutionContext*)` runs on the host side and reads/writes data directly via `GetData<T>()` |
| Ownership resolution | The process of deciding, at export time, whether each fallback node runs on NPU or CPU, and persisting the decision into the epair archive |
| Crossing count | The number of host↔device data transfers (PCIe). The goal of this design is to make it depend on the number of CPU segments rather than the number of CPU operators |

# Overall Description

This section describes the general factors affecting this design: project background, product environment, feature overview, design constraints, and dependencies.

## Software Overview

### Project Introduction

**Current state**: TorchDelegate currently only supports offloading the entire graph to NPU. Compute nodes fall into three categories:

| Scenario | Description | Current support |
|------|------|---------|
| Scenario 1 | Converted to GE built-in operators (`source="converter"`) | ✅ |
| Scenario 2 | Fallback callback operators (`source=""`), calling the PyTorch `PrivateUse1` (NPU) implementation | ✅ |
| Scenario 3 | CPU operators (no NPU execution path) | ❌ Delivered by this feature |

**Problem 1: CPU operators have no representation in the IR.** When the Python-side converter fails to convert a node it creates a mock node with `source=""` ascend_ir, so today every compute node carries ascend_ir. "Should this operator run on NPU or CPU" is not recorded anywhere in the IR and must be added.

**Problem 2: Graph building has a full-offload gate.** `GeGraphBuilder::IsFullyOffloaded()` requires every node to carry ascend_ir, otherwise graph building is abandoned. CPU nodes must be included in the same graph building flow.

**Business driver**: recommendation-network inference is a typical CPU + NPU + CPU three-stage pipeline:

```
Stage 1 (CPU pre-processing)      Stage 2 (NPU core compute)        Stage 3 (CPU post-processing)
Feature extraction, embedding     Embedding projection, attention,  Result aggregation, ranking,
lookup, sequence assembly,        Task Tower, CTR/CVR estimation    scoring, business logic,
length trimming                                                     response packaging
```

Such models have many operators (300–800), small per-operator granularity (1–5 us), and are host bound. Four requirements follow for mixed scheduling:

1. CPU operators must execute in place on host memory, not one PCIe round trip per operator;
2. Data between consecutive CPU operators must stay in host memory; crossing count depends on the number of segments, not operators;
3. NPU subgraphs must stay intact so GE fusion, memory reuse, and multi-stream scheduling keep working;
4. Host-side scheduling overhead must be low; no extra framework-level loop for small operators.

**Implementation path**: CPU operators reuse the existing Fallback Codegen mechanism to automatically generate custom operators registered to the GE HostCpu backend, placed in the same `ge::Graph` as NPU operators, scheduled uniformly by GE. The framework implements no partitioning or copying logic.

### Product Environment

This feature involves four cooperating components:

```
┌──────────────────────────────────────────────────────────────────────┐
│                    PyTorch / torch_npu (same process)                │
│  ExportedProgram ──torchair convert──▶ per-node ascend_ir annotation │
│  PyTorch Dispatcher: PrivateUse1 (NPU impl) / CPU (libtorch impl)    │
└───────────────▲──────────────────────────────────┬───────────────────┘
                │ callBoxed (fallback callback)     │
┌───────────────┴──────────────────────────────────▼───────────────────┐
│                        TorchDelegate (csrc/)                          │
│  Python: ownership resolution → epair serialization (.epair archive)  │
│  C++: EpairModelLoader → FallbackCodegen (generate .so → dlopen reg)  │
│       GeGraphBuilder (graph build: Data/Const/built-in/custom ops)    │
└───────────────────────────────┬──────────────────────────────────────┘
                                │ GeSession::AddGraph / CompileGraph / LoadGraph
                                │ RunGraphWithStreamAsync
┌───────────────────────────────▼──────────────────────────────────────┐
│                             GE (libge)                                │
│  Compile: engine selection → HostcpuEngineUpdatePass → dyn/static     │
│           partition → partitioning → fusion (incl. constant folding;  │
│           HostCpu nodes marked unknown, run by the dynamic executor)  │
│  Runtime: v2 runtime lowering → ExecuteGraph (host kernel/device st)  │
│           host/device memory placement, copy insertion, ordering are  │
│           managed uniformly by GE                                     │
└──────────────────────────────────────────────────────────────────────┘
```

External interfaces stay unchanged:

- `EpairModelLoader` signature and ABI are unchanged;
- The `.epair` archive format only gains optional fields;
- On the GE side only the existing `REG_OP` / `REG_OP_BACKEND` registration surface and existing `GeSession` APIs are used; no new GE interfaces.

## Software Functions

This feature delivers six functions; see the "Feature Requirements & Design" chapter for details:

1. **IR extension and device ownership resolution** (export time, Python): new `device` field; automatic resolution (PrivateUse1 implementation → NPU, CPU-only → CPU, neither → error); decision persisted into the epair archive.
2. **HostCpu custom operator code generation** (before graph build, C++): Fallback Codegen gains a HostCpu variant that generates operators inheriting `HostCpuExecuteOp + ShapeInferOp`, registered via `REG_OP_BACKEND(..., kHostCPU)`, then compiled and loaded.
3. **Graph building and unified GE scheduling** (compile time): CPU nodes enter the graph with host placement; engine assignment, host/device memory placement, copy insertion, execution order, multi-stream, and constant folding are all handled by GE.
4. **Host-side execution and result write-back** (runtime): `Execute` zero-copy wraps host tensors, calls the PyTorch CPU kernel, and writes results directly back to host output memory.
5. **Ownership diagnosability and strict validation**: per-node decision records + export-time ownership report + C++ load-time recap + strict validation switch; no runtime automatic fallback.
6. **Compatibility**: old epair archives keep working on new versions; no local CANN version/capability validation gate is introduced — environment capability surfaces naturally via GE compile-time errors.

## Design Constraints

| # | Constraint | Description |
|---|------|------|
| C1 | Platform neutrality (onetrack) | No chip-specific branches. Low-level calls (data copy, allocator, stream) live entirely inside GE; TorchDelegate does not call new RTS interfaces directly |
| C2 | No configuration for ownership | Ownership is decided purely by automatic resolution; there is no "force this operator onto CPU/NPU" configuration. The only new switch is the strict-validation switch (`require_aten_on_npu`), which does not change ownership results |
| C3 | Data-dependent shapes unsupported | `ShapeInferOp` must derive output shapes at compile time; operators whose output shapes depend on runtime data values (e.g. `nonzero`, `unique`) fail explicitly, without silent degradation |
| C4 | No runtime automatic fallback | Ownership is fixed once at export; a failing NPU operator reports an error with the operator name at runtime and never silently switches to CPU |
| C5 | External API/ABI unchanged | The `EpairModelLoader` signature and ABI are unchanged; models containing CPU nodes go through the same load/execution path |
| C6 | Strict error reporting | External inputs (epair, EP JSON, unknown device values) are parsed strictly; nothing is silently skipped |
| C7 | ABI consistency | The generated .so reuses the existing g++ command line. GE samples use ABI=0; whether the HostCpu path imposes additional ABI constraints is confirmed in the P0.5 phase |
| C8 | CPU operators are NPU fusion barriers | HostCpu custom operators are opaque to GE; NPU operators on both sides cannot fuse across them. Mitigated by keeping the number of CPU operators small via ownership resolution |
| C9 | No graph mutation during concurrent memory reuse | All graph building actions in this design happen during TorchDelegate graph build and GE compile passes, never during the concurrent memory-reuse phase |

## Assumptions and Dependencies

| # | Dependency | Description |
|---|------|------|
| D1 | GE HostCpu capability (key dependency) | Interfaces, lowering, and execution kernels are ready; the minimum companion CANN package version is settled in P0.5 |
| D2 | PyTorch Dispatcher CPU kernels | The deployment environment must have libtorch CPU implementations. `torch_delegate_backend` already links `libtorch_cpu`, and the generated .so link line includes `-ltorch_cpu` |

| D5 | P0.5 interface confirmation results | See the confirmation list at the end of "Changes to Sub-modules" |

# Feature Requirements & Design

## Overview

**One-sentence design**: CPU operators are resolved to `device="cpu"` at export time and persisted into the epair archive; before graph build, one custom operator registered to the GE HostCpu backend (`HostCpuExecuteOp` + `ShapeInferOp`) is generated per CPU operator; its `Execute` calls the PyTorch Dispatcher CPU implementation; CPU operators and NPU operators (GE built-ins + Device-backend custom operators) share one `ge::Graph`, compiled once, executed once, scheduled uniformly by GE. The framework implements no scheduling or copying logic.

**Change overview**:

| # | Change | Location | Size |
|---|------|------|------|
| 1 | Export-time device ownership resolution, persisted into epair | Python side (converter / epair / api) | Small |
| 2 | Fallback Codegen HostCpu variant (incl. `ShapeInferOp` generation) | `csrc/fallback_codegen/` | Medium |
| 3 | Graph build support for host placement and three-way dispatch | csrc/backend/ | Small |
| 4 | Ownership diagnosability | Python + C++ | Medium |
| 5 | GE side | No code changes; existing capabilities only | — |

The "Feature Requirements" sections below specify inputs, processing, and outputs per item; "Changes to Sub-modules" lists file-level changes.

## Feature Requirements

### Requirement 1: IR Extension and Device Ownership Resolution

#### 1. Introduction

Introduce an explicit execution-device marker for nodes and resolve it automatically at export time. The decision is persisted into the epair archive and read-only at runtime.

#### 2. Inputs

- Export target: `ExportedProgram`
- Probe target: the operator target of each fallback node
- Probe source: the PyTorch Dispatcher registry
- Configuration: `EpairConfig`

#### 3. Processing

Step 1, add the `device` field to `NodeIR` (`torch_delegate/converter/base.py:8-12`):

```python
@dataclasses.dataclass
class NodeIR:
    source: str
    ops: list[dict[str, Any]]
    mapping: dict[str, Any] | None = None
    device: str = "npu"                          # ★ new: "npu" | "cpu"
```

Step 2, add the strict-validation switch to `EpairConfig` (no ownership-override fields are added, constraint C2):

```python
require_aten_on_npu: bool = False    # ★ new: error instead of warning when an aten op lands on CPU
```

Step 3, implement automatic resolution `_resolve_device` (called from `torchair_converter.py`):

```python
def _resolve_device(self, target: torch._ops.OpOverload) -> str:
    op_name = f"{target.namespace()}::{target._schema.name}"
    if torch._C._dispatch_has_kernel_for_dispatch_key(op_name, "PrivateUse1"):
        return "npu"                              # NPU impl exists → Device-backend fallback
    if torch._C._dispatch_has_kernel_for_dispatch_key(op_name, "CPU"):
        return "cpu"                              # CPU-only impl → HostCpu-backend fallback
    raise RuntimeError(f"op {op_name} has neither PrivateUse1 nor CPU kernel")
```

Integration: after `TorchAirGEConverter.convert_graph` obtains `ascend_ir_map`, iterate the compute nodes of the converted graph; for mock nodes with `ascend_ir_map[node.name].source == ""`, resolve using `node.target` and write the result back to the corresponding `NodeIR.device`.

Step 4, write the decision into EP JSON. When `writer.py` injects `ascend_ir` it adds the `device` field (around `torch_delegate/epair/writer.py:234-241`):

```json
"ascend_ir": {
  "source": "",
  "device": "cpu",
  "ops": [],
  "mapping": {"inputs": {}, "outputs": {}}
}
```

Step 5, manifest upgrade (`torch_delegate/epair/schema.py:7-26`):

```python
version: int = 2          # ★ 1 → 2
cpu_nodes: int = 0        # ★ new: CPU node counter
```

Compatibility: `device` is optional; when missing it defaults to `"npu"`, equivalent to current behavior; the C++ side keeps full-NPU semantics for manifest version 1.

#### 4. Outputs

- `ep_json_with_ascend_ir.json` annotated with `ascend_ir.device`;
- manifest v2 (with `cpu_nodes`);
- Ownership decision records and the ownership report.

### Requirement 2: HostCpu Custom Operator Code Generation

#### 1. Introduction

Fallback Codegen gains a HostCpu variant. The core idea is maximum reuse: operator prototypes, schema parsing, argument encoding/decoding, and the compile/load pipeline are all reused; only three device-related spots are replaced and one shape-inference generator is added.

#### 2. Inputs

- The EP JSON inside the epair archive (nodes with `ascend_ir.device="cpu"`)
- torch package path and output directory (existing inputs)
- The PyTorch schema of each CPU node (`findSchemaOrThrow`)
- The `tensor_meta` of every output of each CPU node (`ParsedTensorMeta`, the data source for `ShapeInferOp`)

#### 3. Processing

First, the reuse matrix — what stays and what changes:

| Existing component | Location | HostCpu variant handling |
|---------|------|----------------|
| `InputKind` (21 kinds) / `SchemaInfo` / `GetSchemaInfo()` | `fallback_codegen.h:14-67` | Reused as-is |
| Prototype part of `GenerateGeOpReg()` (`REG_OP(...).INPUT/.OUTPUT/.ATTR ... .OP_END_FACTORY_REG` macro chain) | `fallback_codegen.cc:742-863` | Reused as-is (the GE sample `add_custom_ir.h` uses the same `graph/operator_reg.h` macro chain) |
| Operator binding macro | `fallback_codegen.cc:1316` | `REG_AUTO_MAPPING_OP(x)` becomes `REG_OP_BACKEND(x, "x", ge::OpBackend::kHostCPU)` |
| Argument assembly logic (`InputKind`-dispatched args) | `GenerateExecuteMethod` | Reused (IR-indexed accessors match the HostCpu context names and semantics) |
| `CreateNpuTensor()` (`at::kPrivateUse1` zero-copy wrapper) | `fallback_codegen.cc:700-708` | Kept; a corresponding `CreateCpuTensor()` (`at::kCPU`) is added |
| `ReadScalarInput()` (D2H read from device tensor) | `fallback_codegen.cc:723-737` | Not needed in the HostCpu variant (host memory is read directly via `GetData<T>()`) |
| `NPUStreamGuard` + `getStreamFromExternal` | `fallback_codegen.cc:1166-1167` | Not needed in the HostCpu variant (host execution involves no device stream) |
| Output write-back (`MallocOutputTensor` + `aclrtMemcpyAsync` D2D) | Write-back section of `GenerateExecuteMethod` | In the HostCpu variant, write directly to host output memory (`.contiguous()` first for non-contiguous results) |
| inplace handling (`MakeOutputRefInput`) | `fallback_codegen.cc:1262` | Reused (the HostCpu context provides the same family of interfaces) |
| `GenerateFromTargets()` (g++ compile + dlopen) | `fallback_codegen.cc:1566` | Reused as-is (one .so can contain both operator kinds; see the confirmation list for artifact layout) |
| — | — | New: `GenerateShapeInferMethod()` |

The generated HostCpu operator class looks like this (sketch):

```cpp
#include "graph/custom_op.h"    // torch_npu from_blob / NPUStream / NPUGuard no longer needed

namespace ge {
class aten__relu_ final : public HostCpuExecuteOp, public ShapeInferOp {
 public:
  // Replacement 1: base classes change from EagerExecuteOp to HostCpuExecuteOp + ShapeInferOp
  // Replacement 2: context type changes from gert::EagerOpExecutionContext to gert::HostCpuOpExecutionContext
  graphStatus Execute(gert::HostCpuOpExecutionContext *ctx) override {
    const gert::Tensor *ge_input_0 = ctx->GetRequiredInputTensor(0);   // same accessors as the NPU variant
    std::vector<c10::IValue> args;
    args.emplace_back(CreateCpuTensor(ge_input_0));   // Replacement 3: zero-copy host pointer wrapper
    // Scalar parameters are read directly via GetData<T>(); no stream guard; argument assembly logic reused verbatim
    static const auto op_handle = torch::Dispatcher::singleton().findSchemaOrThrow("aten::relu", "");
    auto results = op_handle.callBoxed(args);         // call the PyTorch CPU kernel
    // Write back: after MallocOutputTensor, memcpy directly to the host output memory
    return GRAPH_SUCCESS;
  }

  // New: shape / dtype inference (mandatory for the HostCpu backend)
  graphStatus InferShape(gert::InferShapeContext *ctx) override {
    // Data source: EP JSON tensor_meta (inlined as constants at generation time, or dynamic dims passed through from input shapes)
    return GRAPH_SUCCESS;
  }
  graphStatus InferDataType(gert::InferDataTypeContext *ctx) override {
    // Same as above: inline dtype or pass through by rule
    return GRAPH_SUCCESS;
  }
};

REG_OP_BACKEND(aten__relu_, "aten__relu_", ge::OpBackend::kHostCPU);
}  // namespace ge
```

Net changes: 3 removals (scalar D2H, output D2D, stream guard), 1 addition (`ShapeInferOp` generation), 3 renames (base class, context type, binding macro).

#### 4. Outputs

- A `libcust_opapi.so` containing both Device and HostCpu operators; after `dlopen` they register into the GE custom operator registry (`REG_AUTO_MAPPING_OP` → kDevice; `REG_OP_BACKEND` → kHostCPU).

### Requirement 4: Unified GE Scheduling Pipeline

#### 1. Introduction

This requirement describes what GE does after the graph-build artifacts are handed over: the full path from "registration info" to "host execution". All of it uses existing GE mechanisms — this design changes no GE code, which is why the framework needs no scheduling logic of its own.

#### 2. Inputs

- Custom operators registered to the kHostCPU backend with host-execution lowering markers
- Graph build results carrying host-placement tensor descriptors

#### 3. Processing

The GE-internal pipeline:

| Step | What GE does | Code location |
|------|----------|---------|
| G1 Engine selection | Custom operators registered to kHostCPU are explicitly assigned to the `DNN_VM_CUSTOM` engine with a host-execution lowering func (`host_cpu_custom_op_lower_func`). No device engine is involved, so "must run on CPU" is deterministically guaranteed by the registration method | `dnnengine_manager.cc:76-89` (`SetHostCpuCustomOp`), `:357-368`, `:427-434` |
| G2 Graph unknown marking | Graphs containing host-execution nodes are marked unknown and take the v2 executor path | `mark_graph_unknown_status_pass.cc:22-31,79` |
| G3 Dynamic/static partition | Host-execution nodes are assigned to the dynamic side, affecting the partition boundary (see "Cross-feature Analysis") | `dynamic_shape_partition.cc:58-66`; `graph_split.md` rule 6 |
| G4 Runtime lowering | Host-specialized lowering: allocate inputs/outputs with the kOnHost allocator and generate an `ExecuteHostCustomOp` (or shape-inference variant) kernel node | `custom_node_converter.cc:62-73,203-248` |
| G5 Kernel execution | Fetch the kHostCPU instance from the registry, cast to `HostCpuExecuteOp`, and call `Execute(HostCpuOpExecutionContext*)` | `custom_op_kernel.cc:98-110,240-252` |
| G6 Constant folding | CPU nodes with constant inputs are evaluated at compile time and eliminated from the graph; zero runtime cost | `constant_folding` sample |

Three key conclusions:

1. Ownership is deterministic. Operators registered to kHostCPU go through `DNN_VM_CUSTOM` + host lowering, never through device engine selection, and cannot be re-assigned by the small-shape propagation pass (that pass only acts on operators on device engines). "Must run on CPU" is guaranteed by the registration method.
2. Memory is managed uniformly by GE. Host lowering uses the kOnHost allocator; data between adjacent host nodes stays in host memory; GE inserts copies at host↔device boundaries. Crossings are on the order of CPU segment count, not CPU operator count.
3. Execution is still one call. Externally it is still one `RunGraphWithStreamAsync`; TorchDelegate implements no runner and no unit loop.

#### 4. Outputs

- One compile pass completing host/device memory planning, fusion, multi-stream, and constant folding;
- One execution call completing mixed CPU/NPU graph inference.

### Requirement 5: Runtime Data Flow and Memory Placement

#### 1. Introduction

Describes the runtime data flow and memory ownership, used to verify the four goals stated at the beginning.

#### 2. Inputs

- The ExecuteGraph produced by v2 lowering (host kernel nodes + device operator nodes)
- Tensor descriptors with placement

#### 3. Processing

| Data flow | Implementation |
|--------|------|
| host → host (between adjacent CPU operators) | In-place host memory transfer, no PCIe |
| host → device (CPU segment → NPU segment) | GE inserts an H2D copy in the execution graph |
| device → host (NPU segment → CPU segment) | GE inserts a D2H copy in the execution graph |
| device → device | Unchanged (existing NPU path) |
| CPU operator output memory | `MallocOutputTensor` allocates host memory; lifetime managed by the GE context; generated code never frees explicitly |
| Scalar parameters | Generated as host Const nodes (`plan_fallback_node.cc:151` is already host placement); read directly on host |

#### 4. Outputs

- Zero-copy in-place data flow within a host segment;
- host↔device copy count on the order of segment count, inserted uniformly by GE at boundaries.

### Requirement 6: Ownership Diagnosability and Strict Validation

#### 1. Introduction

Automatic resolution looks at exactly one thing: whether a `PrivateUse1` kernel exists. The following two situations probe identically and cannot be distinguished by the probe itself:

| Case | Meaning | Nature |
|------|------|------|
| A. Expected on CPU | The user only ever wrote a CPU implementation for this operator (e.g. a pure host feature-processing op) | Normal |
| B. Unexpectedly on CPU | The operator should run on NPU but its PrivateUse1 implementation is missing, unregistered, or registered to the wrong overload | Fault, and it manifests as silent degradation: "it runs, results are correct, just slow" |

This requirement addresses it with two complementary mechanisms: mechanism 1 records the decision and its rationale for later attribution; mechanism 2 turns suspicious ownership into an export-time error so attribution is not needed afterwards. Neither changes the ownership result itself.

#### 2. Inputs

- Per-node decision results (node name, target, probes, conclusion)
- The `EpairConfig.require_aten_on_npu` switch
- Export logs / deployment-side load logs

#### 3. Processing

**Mechanism 1: diagnostics log (ownership inventory + rationale)**

1. Record a `DeviceDecision` per node (export-time in-memory record for the ownership report and strict validation, not serialized into the epair archive; C++ load time recaps it from `ascend_ir.device` and the node target namespace):

```python
@dataclasses.dataclass
class DeviceDecision:
    node_name: str        # FX node name
    target: str           # full target, e.g. "torch.ops.aten.nonzero.default"
    namespace: str        # "aten" | custom namespace
    op_name: str          # dispatcher name used for probing, e.g. "aten::nonzero"
    overload: str         # exact overload (detects "registered to the wrong overload")
    device: str           # "npu" | "cpu"
    rule: str             # "converter" | "has_privateuse1" | "cpu_only"
    has_privateuse1: bool
    has_cpu: bool
```

2. Print the full ownership inventory at the end of export (both NPU and CPU sides), graded by namespace:

| Decision | namespace | Level | Rationale |
|---------|-----------|------|------|
| CPU (`cpu_only`) | `aten::` | WARNING | The torch_npu contract should cover aten; missing coverage is abnormal and likely a version mismatch or coverage gap |
| CPU (`cpu_only`) | Custom namespace | INFO | The user may have only written a CPU implementation; expected |
| NPU (`converter` / `has_privateuse1`) | Any | INFO | Normal |

```
    aten::nonzero.default       has_privateuse1=False  has_cpu=True
    aten::_unique2.default      has_privateuse1=False  has_cpu=True
    aten::bincount.default      has_privateuse1=False  has_cpu=True
  expected: custom namespace with CPU-only impl (9):
    my_ops::feature_merge.default   has_privateuse1=False  has_cpu=True
    ...
```

3. C++ load time recaps the same classification (deployment sides usually lack the Python export log), warnings only. Ownership is already fixed in the epair archive; erroring here does not help; the hard constraint is enforced at export time.

**Mechanism 2: strict validation switch**

- Usage: `EpairConfig(require_aten_on_npu=True)`.
- Semantics: if an aten-namespace operator is resolved to CPU, export fails immediately with the full hit list (including `op_name`, `overload`).
- Default `False` (warnings only) so aten operators not yet covered by torch_npu do not block normal exports.
- Typical use: CI / performance-baseline guarding, ensuring no silent degradation to CPU due to torch_npu version changes or missed registrations.
- Custom-namespace operators landing on CPU are unaffected by this switch (expected case).

**Additional constraint: no runtime automatic fallback**

Ownership is decided once at export and fixed into the epair archive; the runtime follows `ascend_ir.device` only. If runtime fallback were allowed, case B would be completely masked (after an NPU kernel throws, silently switch to CPU — correct results but slower with no trace), and both mechanisms above would be pointless. In the current design, a failing NPU operator reports an error with the operator name.

#### 4. Outputs

- The ownership report (full inventory + graded warnings);
- With `require_aten_on_npu=True`: export-time error with the full hit list;
- C++ load-time ownership distribution logs.

### Requirement 7: Compatibility and Capability Validation

#### 1. Introduction

Ensure clear behavior across format evolution: old formats keep their semantics; environment capability is not defensively checked in torch_delegate and surfaces naturally via GE compile-time errors.

#### 2. Inputs

- The epair archive (`ascend_ir.device`, manifest `version` / `cann_version` / `cpu_nodes`)

#### 3. Processing

- Old epair on new version: missing `device` defaults to `"npu"`; manifest v1 keeps full-NPU semantics, zero regression.
- Epair containing CPU nodes on an incapable environment: torch_delegate performs **no** load-time capability validation or local CANN version-check gate; capability issues such as unregistered operators or missing HostCpu backend support surface naturally via GE compile-time errors (with node name and operator type); no defensive handling is added here.
- The minimum CANN version 9.2.0 is the first commercial release torch-delegate supports, documented as a requirement only (see `docs/en/guide/build.md`); `manifest.cann_version` is recorded for diagnostics only and participates in no validation.

#### 4. Outputs

- Compatibility conclusion: old epair fully compatible; new epair fails via GE compile-time errors on environments without HostCpu.

## Non-functional Requirements

### Maintainability

- Code generation maximizes reuse (see the reuse matrix in "Requirement 2"): the HostCpu variant shares argument encoding/decoding, overload resolution, and the compile/load pipeline with the NPU variant, avoiding double maintenance;
- Every generated HostCpu operator `Execute` carries a DEBUG-level node-name log; failure paths have explicit ERROR logs;
- The ownership report carries `rule` / `namespace` fields, machine-readable, filterable by downstream tools.

### Testability

- Python side: `device` field serialization round trip, the three `_resolve_device` branches, and ownership report grading are all unit-testable in pure Python;
- C++ side: generated code text is assertable (contains `REG_OP_BACKEND`, `HostCpuExecuteOp`, without `aclrtMemcpyAsync` / `NPUStreamGuard`); the `PlanNodes` three-way dispatch is unit-testable with the GE stub;
- End to end: new examples cover pure CPU, mixed, and non-adjacent CPU segment shapes.

### Portability

- Zero chip-specific branches (constraint C1); the host execution path does not depend on the NPU model;
- Generated .so ABI and linking follow the P0.5 conclusions (constraint C7).

### Reliability

- Strict errors (constraint C6): unknown device values, missing CPU kernels, data-dependent shapes — all reported at the earliest detectable stage;
- Host output memory lifetime follows the documented GE contract; generated code holds no cross-call state;
- No silent degradation or fallback (constraint C4).

### Platform Requirements

GE is an onetrack component; this feature is chip-agnostic. Low-level calls (copies, allocator, stream) live inside GE through the existing HostCpu/RT2 paths; TorchDelegate generated code adds no RTS call sites.

### Key Techniques / Algorithms

**A. Automatic ownership resolution** (see "Requirement 1"): three branches; no configuration, no priority rules; fixed once at export.

**B. FallbackCodegen HostCpu variant** (see "Requirement 2"): net change is "3 removals, 1 addition, 3 renames"; everything else is reused.

**C. `ShapeInferOp` generation.** The data source is the `tensor_meta` already present in the EP JSON; users need not write Meta implementations:

```
For each output tensor_name of a CPU node:
  meta ← ParsedModel::FindTensorMeta(tensor_name)
  If meta.dynamic_dim_symbols is empty (fully static):
      InferShape    → inline constant shape (meta.sizes)
      InferDataType → inline constant dtype (meta.dtype)
  Otherwise (contains dynamic dims):
      Dynamic dims pass through from ctx->GetInputShape(i); static dims inline as constants
      If a dynamic dim cannot be derived from inputs (data-dependent) → Error (constraint C3)
```

These metas are derived by the Python side at export via `register_fake` (Meta key) and serialized; the C++ `ParsedModel` already parses them fully.

**D. Placement propagation** (see "Requirement 3"): constructor parameter + default; consistent with the existing `ConstNodeSpec` pattern (`graph_build_utils.h:31`).

**E. GE scheduling pipeline** (see "Requirement 4"): all existing GE mechanisms. TorchDelegate does exactly two things: register operators to the correct backend (kHostCPU) and give tensor descriptors the correct placement (host).

### Flow Design

**Phase A · Export (Python)**

1. `export_to_epair(ep, config)` triggers converter graph conversion and produces `ascend_ir_map`;
2. For all mock nodes, `_resolve_device(target)` runs and writes results into `NodeIR.device`;
3. The writer injects `device` into each node's `ascend_ir`; the manifest aggregates `cpu_nodes`;
4. The ownership report is printed (full inventory + graded warnings); if `require_aten_on_npu=True` and any aten→CPU exists, export aborts with an error.

**Phase B · Load and graph build (C++)**

5. `EpairModelLoader` construction: read archive → `FallbackCodegen::GenerateFromModelJson` (generate HostCpu variants, one g++ compile, dlopen registration) → `ParsedModel::Parse` → weight loading;
6. `GeGraphBuilder::Build()`: ownership recap (logged only when CPU nodes exist) → `PreparePlaceholders` → `PlanNodes` (three-way dispatch) → `BindDeferredOutputs` → `BindDeferredEdges` → `FinalizeGraph` → `NormalizeGraph` → `GeGraphOptimizer::Optimize`;
7. `CompileAndLoad`: `GeSession::AddGraph` → `CompileGraph` → `LoadGraph`.

**Phase C · Compile (GE)**

8. Engine selection: kHostCPU custom operators → `DNN_VM_CUSTOM` + host lowering;
9. unknown marking → dynamic/static partition (CPU nodes go to the dynamic side) → partitioning → fusion / memory planning;
10. Constant folding: CPU nodes with constant inputs are evaluated and eliminated at compile time.

**Phase D · Execution (GE + PyTorch)**

11. `RunModelWithStreamAsync(stream, inputs, outputs)` (one call);
12. v2 lowering: host nodes allocate host memory, host/device boundary copies are inserted, the ExecuteGraph is built;
13. `ExecuteHostCustomOp` (with shape inference when needed) calls `HostCpuExecuteOp::Execute`;
14. Inside `Execute`: zero-copy host tensor wrapper → `callBoxed` to the PyTorch CPU kernel → write results directly back to host outputs.

Failure paths: missing CPU kernel, data-dependent shape, unavailable backend → earliest-possible error with node name and reason; a failing NPU operator errors at runtime and never falls back.

| model_mixed (NPU-CPU-NPU) | 3 (1) | 23.1 s | 5.2 s | 7.3 ms | 416 MB |
| model_pure_cpu | 2 (2) | 23.6 s | 0.10 s | 0.7 ms | 415 MB |
| model_non_adjacent | 4 (2) | 22.7 s | 0.12 s | 1.3 ms | 415 MB |
| model_recommender (three-stage) | 7 (2) | 27.0 s | 0.16 s | 1.5 ms | 421 MB |

Conclusions:

- load+codegen is the first cold compile (g++ compiling generated operators, linear in CPU node count, <30 s); with multiple models in one process, subsequent models drop to seconds by sharing the libtorch header compile;
- GE CompileLoad: mixed graphs take the v2 executor (5.2 s for the first graph, including host lowering initialization); subsequent mixed graphs are seconds-level; peak HBM 415–421 MB (including GE/RT residency); CPU outputs and intermediates use host memory and no HBM peak growth with CPU segments was observed (consistent with the "peak HBM does not rise" goal);
- host/device overlap and crossing count are P4 items; msprof can collect timelines on `host_cpu_runner` (the execution phase of `examples/host_cpu_mixed_case/run.sh` can be used directly as the msprof --application entry).

## Acceptance Criteria

1. **Pre-check acceptance (P0.5)**: all three `host_cpu_add_custom` scenarios pass on the target CANN version; all five confirmation items have conclusions filled back into this document; minimum CANN version 9.2.0 settled as a documented requirement (no local version/capability validation gate).
2. **Functional acceptance**: all-NPU models behave and perform identically; pure-CPU models run end to end and match eager CPU element-wise; mixed models (incl. non-adjacent CPU segments and shared-input shapes) run end to end; the real recommendation-network model succeeds on the full path; data-dependent shapes produce a clear Error instead of a crash or silent error.
3. **Accuracy acceptance**: relative error vs eager (CPU) / torchair graph-mode (NPU) baselines within existing thresholds.
4. **Performance acceptance**: end-to-end latency ≤ pure-NPU baseline × 1.05 (head/tail CPU segments); no per-operator PCIe round trips inside CPU segments; constant folding quantified; peak HBM no higher than baseline; compile time ≤ baseline × 1.1.
5. **Interface acceptance**: `EpairModelLoader` external signature and ABI unchanged; usable under both `_GLIBCXX_USE_CXX11_ABI=0/1` (per P0.5 conclusions).
6. **Engineering acceptance**: zero warnings under `-Wall -Wextra -Werror`; full ASAN test pass; `./build.sh`, `./build_test.sh`, `examples/run_all.sh` all green.
7. **Diagnostics acceptance**: ownership report complete (both inventories + `overload`); graded warnings correct; wrong-overload registration cases attributable; `require_aten_on_npu=True` errors at export; C++ load-time recap; no runtime automatic fallback; every HostCpu operator has a DEBUG-level node-name log.

## Risks and Mitigations

| # | Risk | Impact | Mitigation |
|---|------|------|------|
| R1 | Overlap capability between host execution and the device stream is uncertain | CPU segments become serialization points of the device pipeline, negating multi-stream benefits | P4 profiling; if no overlap, evaluate CPU-segment parallelization |
| R2 | Artifact layout and graph build API compatibility unverified (confirmation items 1, 2) | May require reworking `GenerateFromTargets()` or changing packaging | P0.5 measures both paths with a minimal demo; if either fails, follow the GE samples with OPP layout / ES graph build — more work but a clear path |
| R3 | Minimum CANN version raised | Old environments cannot load epair containing CPU nodes | GE compile-time error; pure-NPU models unaffected |
| R4 | dtype/format mapping failure (e.g. CPU kernel returns non-contiguous tensors) | Runtime exceptions buried deep in the GE execution stack | Uniform `.contiguous()` before write-back; log operator name and dtype on failure; full operator coverage tests in P3 |
| R5 | Weak observability (no framework-level segment boundaries) | Debugging spans codegen → generated .so → GE, three layers | Generated-code node-name logs + `DUMP_GE_GRAPH` + profiling |
| R6 | CPU operators remain NPU fusion barriers (constraint C8) | NPU operators on both sides cannot fuse across | Keep CPU operator count small via ownership resolution; an inherent cost of mixed scheduling |

Three items reviewed and excluded as risks (verified):

- "`HostcpuEngineUpdatePass` may re-assign ownership": that pass only acts on operators on device engines; kHostCPU-registered custom operators land on host deterministically at engine selection (see "Requirement 4" G1); shape heuristics cannot re-assign them;
- "`ShapeInferOp` cannot cover data-dependent shapes": a scope boundary with a defined explicit-error handling (constraint C3);
- "HostCpu output memory lifetime unknown": a documented contract; both the GE samples and existing paths rely on the same contract.
