<a id="overview"></a>
## Overview

> Quantization integration CLI params (`--quant-path` / `--quant-method`) in [cli_design.md](../cli/cli_design.md); quantized epair artifact layout, host_weights mechanism, C++ loading side in [export_design.md](../export/export_design.md).

`cann_local_lm/converter/quant/` contains two blocks:

1. **dopt_lm (vendored GPTQ framework)**: performs GPTQ weight quantization on HF models on **NPU/GPU/CPU**, producing per-layer `group_scale` (per-channel × per-group symmetric, offset=0) + GPTQ-corrected fp16 weights, persisted to `trained_quant_weight.pth` or `model.safetensors`. The CANN lightweight tool itself only does fakequant (weights stay fp16), doesn't materialize real int4, doesn't connect to converter export.
2. **Converter-side quantization integration** (`cann_local_lm/converter/swap.py`: orchestration-layer swap; `cann_local_lm/converter/export/quant_swap/`: `materialize.py` / `quant_linear.py` internal materialization; `cann_local_lm/converter/quant/`: `auto_quant.py` / `dopt_wrapper.py`): loads lightweight tool artifacts on **CPU venv + torchair stubs**, materializes into real int4 payload + fp32 scale, replaces `nn.Linear` with `QuantLinear` (forward calls `npu::npu_dynamic_quant` + `npu::npu_quant_matmul`), then `torch.export` produces epair containing `npu_quant_matmul` + `DynamicQuant` nodes.

### Capability Boundary

- **Input**: HF model dir + calibration data (jsonl under `calibrate_sets/`, generated by `download_dataset.py`) + lightweight tool GPTQ artifacts (`model.safetensors` or `.pth`, dir specified by `--quant-path`/lightweight tool `--output-dir`).
- **Output**: epair model dir, whose `*_ep_json_with_ascend_ir.json` contains `npu::npu_quant_matmul` + `npu::npu_dynamic_quant` IR nodes; weight bin contains nibble-packed int4 (int8 storage) + fp32 scale; `model_config.json` contains `quant_info` field.
- **Quantization scope**: all `nn.Linear` (attn q/k/v/o_proj + mlp gate/up/down_proj + gemma4's `per_layer_input_gate` / `per_layer_projection` / `per_layer_model_projection` + `lm_head`), **only `embed_tokens` / `embed_tokens_per_layer` don't go through Linear swap** — they are `nn.Embedding`, consumed by `swap_embeddings_from_dopt` via W8 host gather (converter auto-detects lightweight tool artifacts containing embed scale to do it).
- **Not included**: GPTQ and export memory-link integration (still two-step disk bridge, see [End-to-End Flow](#end-to-end-flow)). CPU running GPTQ **is supported** (dopt_lm `SUPPORTED_DEVICE_TYPES` includes `cpu`, auto-falls-back when no accelerator), but 7B+ Hessian is extremely slow, only suitable for small models/debugging.

## Quantization Toolchain Division of Labor Design

Quantization has many params (layer strategy / group_size / bit / algorithm params percdamp/act_order, etc.); exposing all to the converter CLI would overwhelm users and invite errors. The toolchain divides labor as **lightweight tool step-by-step fine-tuning + CLI one-click export**:

### Design Principles

1. **Lightweight tool step-by-step (fine-tuning)**: the lightweight tool is an independent CLI tool; users can adjust all quantization params — layer strategy (`dopt_config.json`'s `quant_strategy`, auto-generated by `build_layer_strategy` then manually editable), calibration (`config.yaml`'s `ptq_samples`/`cutoff_len`, `train_files` points to `calibrate_sets/`), group_size (`"name;group_size"` syntax). Artifacts land in the dir specified by `--output-dir`.
2. **CLI one-click export (few important params)**: the converter CLI exposes only **two mutually exclusive** quantization entry points; fine params aren't exposed (go through lightweight tool step-by-step):
   - `--quant-path <lightweight-tool-artifact>`: scenario 1, lightweight tool already ran GPTQ, converter consumes artifacts
   - `--quant-method gptq`: scenario 2, converter auto-spawns lightweight tool subprocess to run GPTQ (implemented `auto_quant.py`, see [One-Click Quantization Scheme Selection](#one-click-quantization-scheme-selection))
3. **Converter auto-inference**: scenario 1's `group_size` is auto-derived from the lightweight tool artifact's `group_scale` shape (`swap.py`); `embed` quantization auto-detected (lightweight tool artifact contains `embed_tokens.quant_op...s` then do it); no need for users to repeat params.

### Two Scenarios Comparison

| | Scenario 1: `--quant-path` | Scenario 2: `--quant-method gptq` |
|---|---|---|
| Input | Lightweight tool GPTQ artifacts (dir specified by `--output-dir`) | HF original weights |
| Who runs the lightweight tool | User manually runs lightweight tool (`dopt_wrapper.py`, dopt_config auto-generated) | Converter auto-spawns lightweight tool subprocess |
| Quantization algorithm | GPTQ (lightweight tool, high precision) | GPTQ (lightweight tool, high precision) |
| Format | Inferred from artifacts | Determined by `Quant_INT8-4_ECO` strategy (W4A8) |
| group_size | Auto-inferred (from lightweight tool artifacts) | dopt_config auto-generated (default 128) |
| embed quantization | Auto-detected | dopt_config auto-generated (Quant_Embed_MinMax) |
| Environment | converter CPU stubs (consumes offline artifacts) | converter CPU stubs + subprocess (NPU/GPU/CPU, `_detect_device_type` auto-detects) |
| Status | ✅ implemented | ✅ implemented (scheme C) |
| Fine-tuning | Lightweight tool step-by-step (layer strategy, etc., dopt_config auto-generated then editable) | Lightweight tool step-by-step |

### Mutual Exclusion Constraint

`--quant-path` and `--quant-method` are mutually exclusive (argparse `mutually_exclusive_group`), pick one:
- Neither passed → no quantization (export fp original weight epair)
- `--quant-path <artifact>` → scenario 1
- `--quant-method gptq` → scenario 2
- Both passed → argparse error

Bit-width is determined by dopt_config's `Quant_INT8-4_ECO` strategy (W4A8), no CLI param; scenario 1 infers from artifacts.

> CLI quantization param simplification trade-off: `--quant-group-size` / `--quant-act` / `--quant-embeddings` / `--no-quant-linears` have been removed (group_size/act/embed changed to auto-inference or dopt_config). The converter's min-max fast path (`swap_to_quant_linear` + `materialize_int4`) has been deleted (the lightweight tool only supports GPTQ; min-max has poor precision with no practical value). All fine-tuning is done by the lightweight tool step-by-step.

├── dopt_wrapper.py          Lightweight tool subprocess main (model_define + weight_quant_pipline + auto-generate dopt_config)
├── download_dataset.py      Calibration dataset download script (download/format as jsonl, default output to calibrate_sets/)
├── config.yaml              Lightweight tool GPTQ calibration training config (train_files points to calibrate_sets/, dopt_wrapper via --optimize-config)
├── calibrate_sets/                   Calibration dataset subdirectory (jsonl, generated by download_dataset.py, replaceable/multi-select)
└── dopt_lm/                 vendored GPTQ framework, independent CLI run

cann_local_lm/converter/swap.py                 # Orchestration module (converter root, peer of loader/saver; load→swap→save middle step)
                                           # Absolute import from quant_swap/: lightweight tool artifact loading + Linear→QuantLinear swap + layer strategy parsing

cann_local_lm/converter/quant_entry.py          # Quantization entry facade (converter root): re-export run_auto_quant + swap_from_dopt

> **Migration note** (2026-08-31): `materialize.py` / `quant_linear.py` / `swap.py` migrated out of `cann_local_lm/converter/quant/`. `materialize.py` / `quant_linear.py` landed in `cann_local_lm/converter/export/quant_swap/` (internal materialization); `swap.py` further promoted to `cann_local_lm/converter/swap.py` (converter root, orchestration layer peer of `loader.py` / `saver.py`, absolute import materialize/quant_linear). `quant/` now only retains lightweight tool orchestration (`auto_quant` / `dopt_wrapper`) + vendored `dopt_lm` + calibration data. > **dopt_config.json is not in the quant/ package dir**: the layer strategy config (`{layer_name: quant_strategy}`) is auto-generated by `build_layer_strategy` traversing the model, written into the lightweight tool artifact dir (`--output-dir`/temp disk); converter-side `swap._read_quant_param_map` reads from that artifact dir. **Both scenarios auto-generate**, no manual writing needed. `download_dataset.py`'s default output dir is `calibration_data/`, but this repo's actual artifacts land in `calibrate_sets/` (config.yaml's `train_files` points there).

### Dependency Relationships

```
cann_local_lm/converter/swap.py (orchestration module, peer of loader/saver; load→swap→save middle step)
    │  from cann_local_lm.converter.export.quant_swap.materialize import (...)
    │  from cann_local_lm.converter.export.quant_swap.quant_linear import QuantLinear
    ▼ (absolute import, not relative — swap promoted to converter root)
cann_local_lm/converter/export/quant_swap/__init__.py (materialization internal, re-export 6 symbols)
    ├── materialize.py      ← leaf, only imports torch
    └── quant_linear.py     ← import cann_local_lm.models.fused_ops.ops (registration side effect: npu_quant_matmul + npu_dynamic_quant)

cann_local_lm/converter/quant/auto_quant.py   ← scenario 2 impl (run_auto_quant), subprocess calls dopt_wrapper.py (independent process, doesn't import swap)
cann_local_lm/converter/swap.py               ← scenario 1/2 impl (swap_from_dopt), absolute import quant_swap/
cann_local_lm/converter/quant_entry.py        ← facade, re-export run_auto_quant + swap_from_dopt
                                      ↑
                                      │ external consumer (sole quantization entry)
                  cann_lm_converter.py:
                      from cann_local_lm.converter.quant_entry import run_auto_quant, swap_from_dopt
                      (lazy import inside convert() quantization conditional block; no-quant doesn't import facade → doesn't trigger swap's npu op registration side effects)
```

- **No circular deps**: `materialize ← swap → quant_linear` DAG; `materialize` and `quant_linear` don't depend on each other; `auto_quant.py` and `swap.py` are decoupled (subprocess doesn't import swap).
- **cann_lm_converter accesses the quantization entry via the single `cann_local_lm.converter.quant_entry` facade** (`run_auto_quant` impl in `quant/auto_quant.py` + `swap_from_dopt` impl in `swap.py`, facade re-exports both). `quant_swap/__init__.py` re-exports 6 materialization symbols (`materialize_*` / `transdata_scale` / `restore_scale` / `pack_int4` / `QuantLinear`). `swap_from_dopt` (main path, shared by scenario 1/2, one load sd does both Linear swap + Embedding extraction) + `run_auto_quant` (scenario 2 spawns subprocess). The rest are exposed for testing/offline/future direct calls:
  - `swap_embeddings_from_dopt` (embedding int8+scale extraction, called internally by `swap_from_dopt`; located in `cann_local_lm.converter.swap`)
  - `load_dopt_state_dict` (lightweight tool artifact loading, called internally by `swap_from_dopt`; located in `cann_local_lm.converter.swap`)
  - `materialize_int4_per_group_symmetric` / `materialize_int8_per_channel_symmetric` / `QuantLinear` (located in `cann_local_lm.converter.export.quant_swap`, used via `swap.py` absolute import)

### I/O Positioning

| File | Who reads | How |
|------|------|--------|
| `config.yaml` | `dopt_wrapper.py` (via `--optimize-config`) | Inside the lightweight tool subprocess, **not through converter-side .py** |
| `calibrate_sets/*.jsonl` | Lightweight tool GPTQ calibration (`config.yaml`'s `train_files` points to, relative to CWD = `quant/`) | Inside the lightweight tool subprocess, **not through converter-side .py**; generated by `download_dataset.py` |
| `dopt_config.json` (in artifact dir) | Lightweight tool `--dopt-config` (dopt_wrapper auto-generates and writes into artifact dir) + converter-side `swap._read_quant_param_map` parses layer strategy | **converter-side swap.py also reads** (parses `{layer_name: quant params}` from lightweight tool artifact dir); both scenarios auto-generated, not manual |
| `<artifact dir>/model.safetensors` | `swap.load_dopt_state_dict(quant_path)` (`swap.py`'s `load_dopt_state_dict`, uses `safetensors.safe_open`) | swap.py reads |

**Conclusion**: of the 5 converter-side .py files, `swap.py` (`load_dopt_state_dict` + `_read_quant_param_map`) and `auto_quant.py` (spawns subprocess) do I/O; `materialize.py` / `quant_linear.py` / `dopt_wrapper.py` are completely I/O-free, stateless (`dopt_wrapper.py` runs inside a subprocess, I/O goes through dopt_lm). `config.yaml` / `calibrate_sets/*.jsonl` are all lightweight tool GPTQ-stage inputs; `dopt_config.json` is auto-generated by `build_layer_strategy` into the artifact dir, consumed inside the lightweight tool + parsed by converter-side `swap.py` for layer strategy (`_read_quant_param_map`, scheme C's group_size/bit source).

## Quantization Strategy

### Scheme: W4A8 s8s4 (symmetric)

| Side | Bit-width | Granularity | Symmetric/asymmetric | Scale source | offset |
|----|------|------|-------------|-----------|--------|
| Weight (x2) | int4 (s4) | per-output-channel × per-group(group_size, default 128) | symmetric | GPTQ offline (`group_scale`) | 0 (symmetric, not stored) |
| Activation (x1) | int8 (s8) | per-token dynamic | symmetric | Runtime from x (`npu_dynamic_quant` → `DynamicQuant` IR) | 0 |
| Output | fp16/bf16 | — | — | — | — |

Corresponds to the lightweight tool `strategy.py`'s **`Quant_INT8-4_ECO`** (`dopt_lm/quantizer/strategy.py`):

```python
"Quant_INT8-4_ECO": {
    "weight": {"blocksize": 128, "group_size": 128, "bit": 4, "per_channel": True,
               "weight_algo": "omni_group_min_max"},
    "input":  {"bit": 8, "per_channel": False, "input_algo": "dyn_s8", "unsigned_quant": False},
}
```

- `group_size` can be overridden via `"Quant_INT8-4_ECO;128"` syntax (`strategy.get_optimize_cfg`).
- `dyn_s8` = activation dynamic per-token int8 (signed) — corresponds to W4A8's A8 side; runtime computes per-token scale passed to `quant_matmul_s8s4`'s `x1_scale`.
- `omni_group_min_max` = LSQ-style learnable `quant_alpha` + sigmoid adaptive scale per-group weight quantizer (`dopt_lm/quantizer/qmin_max.py:OmniGroupMinMaxGridWeight`).

<a id="quantization-scope-and-calibration"></a>
### Quantization Scope and Calibration

- **Scope**: all `nn.Linear` (`q_proj/k_proj/v_proj/o_proj/gate_proj/up_proj/down_proj/per_layer_input_gate/per_layer_projection/per_layer_model_projection` + `lm_head`).
- **lm_head quantization** (important): `swap.DEFAULT_SKIP = ("embed_tokens", "embed_tokens_per_layer")` (`swap.py`'s `DEFAULT_SKIP`) **does not include `lm_head`** → `lm_head` is consumed as a large NPU-side Linear via W4 QuantLinear. The converter deployment form is host-embed + NPU-lm_head (`tie_word_embeddings` must be untied: embed on host, lm_head on NPU; different compute domains can't share weights).
- **embed_tokens / embed_tokens_per_layer**: are `nn.Embedding` (not Linear, Linear swap doesn't touch them), consumed by `swap_embeddings_from_dopt` via W8 host gather — converter auto-detects lightweight tool artifacts containing embed scale to do it (embed externalized, no embed_tokens node in graph, `--use-embeddings` defaults True).
- **Calibration data**: jsonl files under `calibrate_sets/` subdirectory (generated by `download_dataset.py`, supports ultrachat_200k / fineweb_edu / toolbench / bfclv4 / c4 / coig_cqia / mc4 seven types; `config.yaml`'s `train_files` points to specific files, replaceable/multi-select).
- **`config.yaml` actual content** (`quant/config.yaml`):

  ```yaml
  dataset:
    # Calibration set: jsonl under calibrate_sets/ (generated by download_dataset.py, replaceable/multi-select)
    train_files:
      - "calibrate_sets/calibrate_c4.jsonl"
    ptq_samples: 1024
  cutoff_len: 512

  extra_training_config:
    fp16: true   # GPTQ runs fp16 + persists fp16, avoids lightweight tool default fp32 doubling artifacts (CPU dispatch auto-falls-back to float32)
  ```

  > `ptq_samples=1024` (not the 128 misremembered in historical docs). On CPU device, dopt_lm `dispatch_dtype` auto-falls-back to `float32` (`train.py` CPU branch); the fp16 flag doesn't conflict.

- **GPTQ runs on HF model**: the lightweight tool depends on `transformers.AutoModelForCausalLM` + `accelerate` dispatch, doesn't modify the lightweight tool; quantization params are ported to the cann_local_lm model by layer name (both have consistent naming: `model.layers.N.self_attn.q_proj`, etc.).

### Lightweight Tool Measured Quantization Scope (gemma4-E4B, 346 lightweight tool modules)

`dopt_config.json` (796 lines) config: `embed_tokens` → `Quant_Embed_MinMax` (bit=8 int8 per-channel, host gather), `lm_head` and other Linear → `Quant_INT8-4_ECO` (default group 128). The lightweight tool artifacts' `lm_head.weight` and `model.embed_tokens.weight` are **effectively untied** (max diff ≈0.01 = GPTQ correction; lm_head is the GPTQ-corrected version for W4, embed is the original for W8).

- **bit distribution**: bit=4 totals 344 (attn q/k/v/o_proj + mlp gate/up/down_proj + PLE per_layer_input_gate/per_layer_projection/per_layer_model_projection + lm_head), bit=8 totals 2 (embed_tokens + embed_tokens_per_layer).
- **gemma4 KV sharing**: `k_proj`/`v_proj` only 0..23 (24 layers) have independent weights; the latter 18 layers (24..41) reuse earlier-layer KV with no independent k/v_proj — determined by model structure, not missed quantization.

### One-Click Quantization Scheme Selection

> **Design principle**: the lightweight tool directly uses the `transformers` library source for quantization (`AutoModelForCausalLM.from_pretrained` + Catcher/hooks), **does not modify the lightweight tool to adapt to cann_local_lm models**. GPTQ runs on HF transformers models; the converter consumes its state_dict artifacts and swaps to the cann_local_lm model. This keeps the lightweight tool consistent with transformers upstream, low maintenance cost.

Currently two steps via disk bridge (`--quant-path`). To implement CLI one-click quantization (user passes one command, converter auto-runs GPTQ + swap + export), there are three schemes:

#### Three Schemes Comparison

| Dimension | A. Modify lightweight tool to run cann_local_lm | B. Memory bridge (in-process) | C. subprocess calls lightweight tool ✅selected |
|------|------|------|------|
| Fixes two instances | ✅ fixes (single cann_local_lm instance) | ❌ still two instances (HF vs cann_local_lm) | ❌ still two instances (HF inside subprocess) |
| Memory peak | ✅ 1× | ❌ 3-4× (cann_local_lm + lightweight tool 2× HF + sd) | ⚠️ 2× (lightweight tool 2× inside subprocess + main process cann_local_lm, separate processes) |
| Env conflict | ⚠️ single process but still needs NPU | ❌ converter process needs both CPU stubs(export) + NPU(GPTQ), contradictory | ✅ avoided (subprocess NPU/GPU/CPU, main process CPU stubs) |
| Change volume | ❌ largest (lightweight tool adapts to both models + vendored diff) | ✅ small (three change points) | ✅ small (converter adds subprocess call) |
| lightweight tool code change | ❌ large (get_llama/llama_sequential/visible_type_dict) | ⚠️ medium (add ptq_quant_produce_state_dict) | ✅ none (reuse lightweight tool CLI) |
| lightweight tool global state risk | ❌ high (in-process args global singleton/reentrancy) | ❌ high (in-process) | ✅ isolated (subprocess independent) |
| Truly one-step | ✅ yes | ✅ yes (in-process) | ❌ no (automated two-step, converter triggers subprocess + swap) |
| Maintenance cost | ❌ high (follow lightweight tool vendored diff) | ⚠️ medium (lightweight tool adds function maintenance) | ✅ low (lightweight tool unchanged) |
| 7B+ applicability | ✅ good (1×) | ❌ poor (3-4×) | ⚠️ medium (2× separate processes) |

#### Selected Scheme C: subprocess calls lightweight tool

**Reasons**:
1. **Uphold design principle**: lightweight tool uses transformers source for quantization, zero changes (scheme A modifying lightweight tool to adapt to cann_local_lm violates this principle)
2. **Avoid env conflict**: converter main process keeps CPU stubs (export phase), subprocess uses NPU/GPU/CPU env (GPTQ phase, dopt_lm `SUPPORTED_DEVICE_TYPES` includes `cpu`), two envs isolated (scheme B env conflict unsolvable)
3. **lightweight tool global state isolation**: subprocess independent, avoids `ptq_loop.py`'s `args` global singleton/reentrancy risk
4. **Low maintenance cost**: lightweight tool unchanged, just follow transformers upstream

**Cost**: not truly one-step (subprocess running lightweight tool is still two steps, just one-click from user perspective); artifact transfer (temp disk IO or memory pipe)

#### Scheme C Design

converter `--quant-method gptq` one-click trigger: main process spawns `dopt_wrapper.py` subprocess (NPU/GPU/CPU env, auto-detected by `_detect_device_type`, falls back to `cpu` when no accelerator) to run GPTQ → artifacts to temp disk → converter swap + export. Impl in `cann_local_lm/converter/quant/auto_quant.py` (`run_auto_quant`).

```
converter main process (CPU stubs)                      subprocess (NPU/GPU/CPU env)
─────────────────────────────                     ─────────────────────────
convert(--quant-method gptq)                      python dopt_wrapper.py
  ├─ run_auto_quant → spawn subprocess ───────→     ├─ build_layer_strategy auto-generates dopt_config
  │   (system Python + subprocess env + cwd=quant/)  ├─ weight_quant_loop (GPTQ, NPU/GPU/CPU)
  │                                                  └─ artifacts → temp disk model.safetensors
  ├─ wait subprocess done
  ├─ swap_from_dopt(model, temp disk)               # Linear swap + embed extraction (one load sd, reuse --quant-path logic)
  └─ save_epair_prefill_decode(...)                  # export
```

Target command:
```bash
DEVICE=npu python cann_lm_converter.py \
  --hf-path /path/to/hf --output-dir /path/to/out \
  --quant-method gptq
# converter auto: detect device → spawn lightweight tool subprocess (GPTQ) → temp disk → swap → export
# (--quant-method gptq mutually exclusive with --quant-path; device auto-detected by _detect_device_type)
```

**Two-phase implementation**:
1. **Phase 1 (temp disk, implemented)**: subprocess artifacts to temp disk (`tempfile`), converter reads temp disk to swap. Simple, reuses `--quant-path` logic. Cost: temp disk IO.
2. **Phase 2 (memory pipe, TODO)**: subprocess artifacts to memory pipe (pickle/mmap/shared memory), converter reads pipe to swap. Saves IO but complex. 7B+ large models benefit.

**Implementation status** (`auto_quant.py` + `dopt_wrapper.py`):
1. **subprocess env** ✅: `PYTHONPATH` adds `quant/` + `DEVICE=<npu|cuda|cpu>` + `LD_LIBRARY_PATH` removes stubs; `DOPT_PYTHON` env var can override system Python path
2. **calibration path** ✅: subprocess `cwd=cann_local_lm/converter/quant/` (config.yaml's `train_files` points to `calibrate_sets/*.jsonl`, relative to CWD)
3. **dopt_config generation** ✅: both scenarios auto-generated by `build_layer_strategy` traversing model layer names (written into artifact dir), **no manual writing needed**; scenario 2 inside subprocess (dopt_wrapper), scenario 1 offline by the use case (`examples/run_pd6_cases.sh:gen_dopt_config`) inline `build_layer_strategy` traversing cann_local_lm `artifact.model` to generate temp cfg for raw `dopt_lm.opt_main`
4. **subprocess failure handling** ✅: exit code non-0 raises `RuntimeError`, retains temp artifact path for debugging
5. **device detection** ✅: `_detect_device_type` prioritizes parent process `DEVICE` (including `cpu`), spawns detection (`torch_npu`/`torch.cuda`) only if unset; disables `ASCEND_SLOG_PRINT_TO_STDOUT` to prevent CANN log polluting stdout parsing; **falls back to `cpu` when no NPU/GPU** (dopt_lm supports CPU float32, 7B+ Hessian extremely slow, only small models/debug, no longer errors)
6. **dopt_wrapper main** ✅: `model_define` (transformers fp16) + `weight_quant_pipline` (GPTQ) landed, `--hf-type-save` produces safetensors

9. **temp disk cleanup** ⏳ TODO: currently not cleaned (retained for debugging), 7B+ large files need `shutil.rmtree`
10. **measured verification** ⏳ TODO: cann_local_lm layer name vs HF matching, subprocess env runs, calibration matching

> `--quant-path` (consumes existing lightweight tool disk artifacts) retained as fallback, mutually exclusive with `--quant-method gptq` (auto-spawns lightweight tool). subprocess device auto-detected by `_detect_device_type` (falls back to `cpu` when no accelerator).
### `materialize.py` — Weight Materialization Pure Functions

Pure function module, materializes fp16/bf16/fp32 `nn.Linear` weights `[out, in]` into quantization payload + per-group/per-channel scale. **Stateless, no side effects, no external I/O**. It's the "numerical core" of the whole quantization chain.

| Function/constant | signature | param count | purpose |
|------|------|--------|------|
| `_SCALE_MASK` | module-level constant `0x00000000FFFFE000` | — | Bit mask: truncates mantissa low 13 bits + clears high 32 bits (persistence format) |
| `transdata_scale` | `(scale_fp32: Tensor) -> Tensor` | 1 | fp32 → int64 bit pattern + `& _SCALE_MASK` (persistence format conversion). torch has no uint64, uses int64 (same bit pattern) |
| `restore_scale` | `(scale_packed: Tensor) -> Tensor` | 1 | int64 (bit pattern + mask) → fp32 (mantissa low 13 bits are 0, reduced precision). Scheme A legacy, currently not called but retained |
| `pack_int4` | `(q: Tensor) -> Tensor` | 1 | Nibble-pack signed int4 (stored as int8) into `[..., k//2]` int8; byte[i] = int4(k=2i+1)<<4 \| int4(k=2i). Private helper, not in `__all__` |
| `materialize_int4_per_group_symmetric` | `(weight, scale, group_size, signed=True, nbits=4, packed=False) -> (Tensor, Tensor)` | **6** | **Main path**: quantize with lightweight tool pre-computed per-group scale (GPTQ-optimized), scale returned as-is. Called by `_swap_linear_from_sd` |
| `materialize_int8_per_channel_symmetric` | `(weight, scale, signed=True) -> (Tensor, Tensor)` | 3 | 8-bit per-row (per-vocab-channel) symmetric quantization (matches lightweight tool `Quant_Embed_MinMax`), produces (int8 `[vocab,hidden]`, fp32 scale `[vocab]`). Called by `swap_embeddings_from_dopt` |

**Internal numerical pipeline** (for `materialize_int4_per_group_symmetric`, 4 steps):
1. Preprocessing: `w = weight.detach().float()` + shape validation (`in_f % group_size == 0`, `scale.shape == (out_f, in_f // group_size)`).
2. scale broadcast: `scale_exp = scale.float().repeat_interleave(group_size, dim=-1)` to `[out, in]`.
3. Quantize + clamp: `q = torch.round(w / scale_exp)`; signed → `clamp(-qmax, qmax)` (4-bit → `[-7, 7]`); unsigned → `clamp(0, 2*qmax+1)`.
4. packing + return: `q.to(int8)`; `packed=True` → `pack_int4(q)` returns `[out, in//2]`; else returns `[out, in]`. Returns `(payload, scale.to(float32))`.

> **Code style observation**: `materialize_int4_per_group_symmetric` has **6 params** (exceeds AGENTS.md's "no more than 5 params" principle). Suggest aggregating `signed`/`nbits`/`packed` three quantization-format params into an `Int4Spec`/`QuantFormat` dataclass (the three jointly describe "int4 encoding format", semantically cohesive), making the signature 4 params. Currently not split.

> **docstring legacy**: the file header docstring still says "int4 signed values stored 1/byte = unpack" + "this module is a placeholder unpack+signed impl, first get the Python flow working, CANN alignment later", but actually `pack_int4` already implements nibble-pack and `materialize_int4_per_group_symmetric` supports `packed=True`, long since not a placeholder. docstring to update.

### `quant_linear.py` — Export-use QuantLinear

Defines `QuantLinear(nn.Module)`, as the surrogate for `nn.Linear` on the export path. Its `forward` explicitly calls `torch.ops.npu.npu_dynamic_quant` (activation quantization) + `torch.ops.npu.npu_quant_matmul` (weight int4 matmul), so the graph produced by `torch.export` directly has these two custom op nodes (not `aten.mm`/`MatMul`), later mapped to `ge.QuantBatchMatmulV4` via `_quant_matmul_converter.py`.

```python
class QuantLinear(nn.Module):
    def __init__(self, weight_q: Tensor, weight_scale: Tensor,
                 group_size: int, bias: Tensor | None = None,
                 act_quant: bool = True):  # 5 params (excluding self)
        # act_quant=False directly raise NotImplementedError (W4A16 not supported)
        # weight_q: int8 [k//2, n] nibble-packed (pre-transposed) → register_buffer
        # weight_scale: fp32 [k//g, n] (pre-transposed) → register_buffer
        # bias is None → self.bias = None (forward passes None, GE converter side stuffs dummy)

    def forward(self, x: Tensor) -> Tensor:
        x_q, x_scale = torch.ops.npu.npu_dynamic_quant(x)          # activation s8 per-token
        out = torch.ops.npu.npu_quant_matmul(
            x_q, self.weight_q, self.weight_scale,
            pertoken_scale=x_scale,                      # per-token act scale (kwarg)
            bias=self.bias,                              # None when source Linear has no bias
            group_sizes=[1, 1, self.group_size],         # V4 3-element [m,n,k]; K-group at index [2]
            output_dtype=_OUT_DTYPE_CODE.get(x.dtype, 5),  # fp16=5, bf16=7, fp32=6
            transpose_x1=False,
            transpose_x2=False,                           # x2 already pre-transposed to [k//2, n], meta takes N=x2.size(-1)
        )
        return out
```

The module-level constant `_OUT_DTYPE_CODE = {torch.float16: 5, torch.bfloat16: 7, torch.float32: 6}` maps torch dtype to GE output_dtype code. `from cann_local_lm.models.fused_ops import ops as _fused_ops  # noqa: F401` is for the side effect of registering the two custom ops `npu_quant_matmul` + `npu_dynamic_quant`, not directly using its symbols.

**Conventions** (path C', s8s4 symmetric, offset=0):
- weight_q / weight_scale **pre-transposed** to `[k//2, n]` / `[k//g, n]` (swap.py materialize then `transpose(-1,-2)`); `transpose_x2=False` (meta takes `N = x2.size(-1)`, GE converter hardcodes `transpose_x2=False`).
- activation: `npu_dynamic_quant` → int8 x1 + per-token fp32 x1_scale (passed as `pertoken_scale` kwarg).
- bias optional `[n]` (output dtype); when source Linear has no bias, forward passes None, but GE converter `_quant_matmul_converter.py`'s dummy bias workaround stuffs dummy zeros[N] (CANN V4 `InferNDimWithBias` not supporting bias=nullptr).
- `group_sizes=[1, 1, g]`: V4's 3-element [m,n,k] 48-bit encoding, K-group at index [2].

## Path C' — npu_quant_matmul → V4 Operator Spec and Implementation Status

> Currently adopted: reuse CANN native `npu::npu_quant_matmul`, FX→GE converter `_quant_matmul_converter.py` maps to `ge.QuantBatchMatmulV4`, lands on pre-compiled kernels via V4→V3 TBE fusion.
>
> **History**: earlier selected scheme A (in-house `cann_local_lm::quant_matmul_s8s4`, using fp32 scale to do `q*scale` dequantization to bypass CANN V4's uint64/FP19 and V4→V3 fusion downgrade). ### Compute Semantics (s8s4 symmetric, offset=0)

Let activation `x1` `[b, m, k]`, weight `x2` `[n, k]` (nn.Linear natural orientation, after materialize pre-transposed to `[k, n]`/`[k//2, n]`), group_size `g` (`k%g==0`):

```
y[b,m,n] = Σ_k ( x1_q[b,m,k] · x1_scale[b,m] ) · ( x2_q[n,k] · x2_scale[n, k//g] ) + bias[n]
```

- `x1_q` int8 (per-token dynamic symmetric, one scale per row), `x2_q` int4 (per-channel×per-group symmetric, one scale per (n,group)).
- `x1_scale[b,m]` is per-token (V4's `pertoken_scale` input), **can be factored out of the k summation**.
- `x2_scale[n, k//g]` is per-group (V4's `x2_scale`/V3's `scale` input), **inside the k summation** (each group of g elements shares one, broadcast per-group during dequantization, can't be factored out of the summation).

### Operator Signature (`npu::npu_quant_matmul`)

| Direction | name | dtype | shape | semantics/source |
|---|---|---|---|---|
| in | `x1` | int8 | `[b, m, k]` | Quantized activation from `npu_dynamic_quant` |
| in | `x2` | int4 (packed int8) | `[k//2, n]` (**pre-transposed**) | nn.Linear weight materialized to int4 nibble-packed |
| in | `scale` | fp32 | `[k//g, n]` (**pre-transposed**) | per-K-group × per-output-channel, from GPTQ (V4's `x2_scale`) |
| in (opt) | `pertoken_scale` | fp32 | `[b, m]` | per-token scale, from `npu_dynamic_quant` (V4's `x1_scale`) |
| in (opt) | `offset` | fp32 | `[k//g, n]` | per-group offset (V4's `x2_offset`); currently verified must be all 0 (symmetric only) |
| in (opt) | `bias` | same as output | `[n]` | fused add; None → GE converter stuffs dummy zeros[N] |
| attr | `group_sizes` | int[3] | — | V4 48-bit encoding `[m, n, k]`, K-group at index [2] (`[1, 1, g]`) |
| attr | `output_dtype` | int | — | 5=fp16 / 7=bf16 / 6=fp32 |
| attr | `transpose_x1` | bool | — | default False (activation never transposed) |
| attr | `transpose_x2` | bool | — | default False (x2 already pre-transposed to `[k//2, n]`, meta takes `N=x2.size(-1)`) |
| out | `y` | fp16/bf16 | `[b, m, n]` | — |

> **Full schema** (`quant_matmul.py`'s schema definition): `npu_quant_matmul(Tensor x1, Tensor x2, Tensor scale, *, Tensor? offset, Tensor? pertoken_scale, Tensor? bias, int? output_dtype, int? x1_dtype, int? x2_dtype, int? pertoken_scale_dtype, int? scale_dtype, int[]? group_sizes, Tensor? y_scale, bool transpose_x1=False, bool transpose_x2=False) -> (Tensor y)`. `x1_dtype`/`x2_dtype`/`*_scale_dtype` are for Bitcast (mxfp4/a8w4 float dtype branches, deleted).

### GE Converter Key Techniques (`_quant_matmul_converter.py`)

1. **V4 full IR**: `ge.QuantBatchMatmulV4(x1, x2, bias, x1_scale=pertoken_scale, x2_scale=scale, y_scale, x1_offset=None, x2_offset=offset, y_offset=None, x2_table=None, dtype, transpose_x1=False, transpose_x2=False, group_size)`. All inputs including None placeholder, letting V4→V3 TBE fusion correctly map `x2_scale` to V3's `scale` input (see Appendix A.2.2 index mapping).
2. **dummy bias zeros[N] workaround**: when bias=None stuffs `ge.Const([0.0]*N, dtype=1)`. CANN V4 `InferNDimWithBias` doesn't support bias=nullptr (would infer bias shape from x1's M dim and compare with N, reporting "dimensions a(M) and b(N) must be same"). Dummy value 0 doesn't affect matmul result.
3. **group_sizes 48-bit encoding**: `group_size = (group_m << 32) + (group_n << 16) + group_k`, validates three elements ∈ [0, 65535]. `[1, 1, g]` → K-axis groups g.
4. **Deleted a8w4/mxfp4 branches**: to remove torch_npu dependency, deleted `float4_e2m1fn_x2`/`float8_e8m0fnu` etc. dtype constant branches that have no torch equivalent (`x1_dtype`/`x2_dtype`/`*_scale_dtype` Bitcast paths retained but converter doesn't actively use). Restoring a8w4 needs re-introducing torch_npu dependency or building a dtype constant mapping (see `quant_matmul.py` file header comment).
5. **transpose_x1/x2 hardcoded False**: meta takes `N = x2.size(-1)`, so x2 must be pre-transposed by swap.py to `[k//2, n]` so `size(-1) = n = out_features`.

### CANN V4 Limitations and Workaround Checklist

| Limitation | workaround | location |
|------|-----------|------|
| `InferNDimWithBias` doesn't support bias=nullptr | stuff dummy zeros[N] (value 0 doesn't affect result) | `_quant_matmul_converter.py`'s dummy bias workaround |
| V4→V3 fusion needs full IR to correctly map x2_scale | use `ge.QuantBatchMatmulV4` full IR (all inputs including None placeholder) | `_quant_matmul_converter.py`'s V4 full IR construction |
| meta takes `N = x2.size(-1)`, ignores transpose_x2 | swap.py materialize then pre-transpose weight_q/weight_scale to `[k//2, n]`/`[k//g, n]` | `swap.py`'s pre-transpose |
| No torch_npu → no schema/fake-meta | `_library.py` self-provides (`_HAS_TORCH_NPU=False` path) + CPU PoC impl | `quant_matmul.py`'s fake-meta + CPU impl |

### Historical Archive: Scheme A In-House Kernel Spec (deprecated, retained for reference)

> The following is the I/O constraints and pipeline reference for scheme A `cann_local_lm::quant_matmul_s8s4` in-house kernel, **deprecated** (code switched back to `npu::npu_quant_matmul`), retained only as a historical decision archive. If CANN V4 integer int8/int4 path hits bottlenecks again in the future, can reference this spec to restart in-house.

**Key differences between scheme A and path C'**:

| Dimension | Scheme A (in-house, deprecated) | Path C' (currently adopted) |
|---|---|---|
| Operator | `cann_local_lm::quant_matmul_s8s4` | `npu::npu_quant_matmul` |
| GE op | In-house GE op | `ge.QuantBatchMatmulV4` (CANN native) |

| bias | truly optional (no dummy) | None → GE converter stuffs dummy zeros[N] |
| scale dequantization | fp32 `q*scale` (bypasses V4 uint64) | Goes through CANN V4→V3 fusion (depends on pre-compiled kernel) |

**Scheme A kernel internal pipeline reference** (for implementer reference when in-house):

Weight-side per-group scale is inside the k summation, so the kernel must dequantize the int4 weight per-group before cube accumulation:

1. L1/L0B load does int4→int8 unpack, fetches `x2_scale` per-group broadcast;
2. cube does **int8×int8 → int32** accumulation (hits the W8A8 verified int8 cube path, avoids FP19/uint64);
3. fixpipe stage multiplies `x1_scale` (per-row, can post-multiply) + `bias` → cast fp16/bf16.

This pipeline makes s8s4 numerics land on "int8 cube + fp32 scale dequantization" semantics, the key to bypassing CANN V4 failure points.

## weight_scale Persistence Format: fp32→uint64 Bit Pattern Conversion

> Convert `QuantLinear.weight_scale` (per-group fp32 scale produced by GPTQ) via bit mask `& 0x00000000FFFFE000` to uint64 bit pattern for persistence. Truncates mantissa low 13 bits (precision 23→10 bits) + truncates high 32 bits (value uses only low 32 bits). Integration location: `materialize.transdata_scale` / `restore_scale` + `epair_utils.inline_weight_scale_dtype` + saver `_pack_weights_to_dir`.
>
> Last updated: 2026-08-25
>
> **Note**: the "scheme A/B" in this section are **two integration schemes for weight_scale persistence format** (scheme A modifies QuantLinear buffer / scheme B only converts at persistence), a different conceptual dimension from the [operator selection](#path-c-npu_quant_matmul-v4-operator-spec-and-implementation-status)'s "scheme A in-house quant_matmul_s8s4". Scheme B (persistence-only) currently adopted.

### Background: bit mask `0x00000000FFFFE000` meaning

```
mask 0x00000000FFFFE000 (64-bit)
     └──────┬──────┘└──────┬──────┘
       high 32 bits=0      low 32 bits=0xFFFFE000
                    └──┬──┘└──┬──┘
                      all 1    bit12-0=0
                    (bit31-13 retained)
```

| Bit segment | mask bit | result | float32 meaning |
|------|--------|------|-------------|
| bit 63-32 | all 0 | cleared | (value uses only low 32 bits, equivalent to uint32 range) |
| bit 31 | 1 | retained | sign bit |
| bit 30-23 | all 1 | retained | exponent (8 bits) |
| bit 22-13 | all 1 | retained | mantissa high 10 bits |
| bit 12-0 | all 0 | cleared | **mantissa low 13 bits** (precision 23→10 bits) |

→ Retains sign + exponent + mantissa high 10 bits, truncates mantissa low 13 bits. After dequantization restore it's still valid fp32, but reduced precision (~7→~3 decimal digits).

### Two Integration Schemes

#### Scheme A: Modify QuantLinear (buffer stores int64)

`QuantLinear.weight_scale` buffer directly stores int64; at forward, `restore_scale` (int64→int32→fp32 bit restore) then passes to `npu_quant_matmul`.

```python
# materialize.py
def transdata_scale(scale_fp32):  # fp32 bit pattern → int64 + mask
    bits = scale_fp32.contiguous().view(torch.int32).to(torch.int64)
    return bits & 0x00000000FFFFE000

def restore_scale(scale_packed):  # int64 → fp32 (mantissa low 13 bits are 0)
    return scale_packed.to(torch.int32).view(torch.float32)
```

```python
# quant_linear.py (scheme A)
self.register_buffer("weight_scale", weight_scale.to(torch.int64))  # int64
def forward(self, x):
    weight_scale_fp32 = restore_scale(self.weight_scale)  # int64 → fp32
    out = torch.ops.npu.npu_quant_matmul(x_q, self.weight_q, weight_scale_fp32, ...)
```

- **swap.py**: after materialize calls `transdata_scale` to convert fp32→int64, stores into QuantLinear buffer.
- **torch.export trace**: `restore_scale` generates Cast(int64→int32) + view(int32→fp32) graph nodes.
- **ep_json dtype**: `DT_INT64` (torch buffer is int64, torch.export auto-infers).
- **saver**: directly packs int64 tensor bytes (no special handling).
- **C++**: reads per ep_json's `DT_INT64` (`DecodeBytesAs<int64_t>`), equivalent uint64.

#### Scheme B: Persistence-only conversion (buffer stays fp32, saver converts to int64 at pack time) ✅ currently adopted

`QuantLinear.weight_scale` buffer stays fp32 (compute path unchanged, forward directly passes to `npu_quant_matmul`, no Cast graph node). Only saver at pack time recognizes weight_scale and calls `transdata_scale` to convert to int64; ep_json post-processing re-marks dtype from `DT_FLOAT` to `DT_INT64`.

```python
# quant_linear.py (scheme B) — unchanged
self.register_buffer("weight_scale", weight_scale.to(torch.float32))  # fp32
def forward(self, x):
    out = torch.ops.npu.npu_quant_matmul(x_q, self.weight_q, self.weight_scale, ...)
```

```python

                           equivalent uint64 bit pattern)
```

### C++ Read Guarantee Chain

```
ep_json tensor_values: weight_scale dtype = "DT_INT64" (kDtypeLong=5)
    ↓ C++ Pt2DtypeFromGeString("DT_INT64") → pt2::kDtypeLong
    ↓ ElementSizeForPt2Dtype(kDtypeLong) → sizeof(int64_t) = 8 bytes/element
    ↓ DecodeBytesAs<int64_t>(bytes, size) → decode as int64
int64 bytes = uint64 bytes (8-byte little-endian, same bit pattern)
    ↓ C++ can reinterpret_cast<uint64_t*> interpret
equivalent to reading as uint64 ✓
```

**torch has no uint64 dtype**, uses int64 storage (same bit pattern, bitwise `&` results identical). `BuildTensorHolder` also validates `Product(dims) * element_size == byte_size` (`WEIGHT_SIZE_MISMATCH` guard); wrong dtype marking directly errors.

## Known Issues and Legacy

1. **unsigned int4 not supported**: `_swap_linear_from_sd` (`swap.py:291-295`) reads the lightweight tool artifact's `unsigned_quant`, validates must = 0 (symmetric signed `[-8, 7]`). Non-0 (unsigned int4 `[0, 15]`) touches CANN int4 signed/unsigned encoding conventions, currently directly `ValueError` rejected. The lightweight tool default `Quant_INT8-4_ECO`'s `unsigned_quant=False`, so the main path doesn't trigger.
2. **asymmetric offset not supported**: `_swap_linear_from_sd` (`swap.py:296-301`) reads the lightweight tool artifact's `offset`, validates must be all 0 (symmetric). Non-zero offset (asymmetric) `NotImplementedError` — `npu::npu_quant_matmul` only supports symmetric offset=0. The lightweight tool's `weight_q_params_adapter_into_dopt` zeroes offset (`offset=torch.zeros_like(...)`), so the main path doesn't trigger. The lightweight tool's `QuantizerFuncIntOffset` dequantizes `w_fp=(q-offset)*scale`; if asymmetric is supported in the future, need to align op's offset semantics + per-group `repeat_interleave` expansion.
3. **CPU-only adaptation**: converter-side GPTQ can't run (needs NPU/GPU + calibration). **`--quant-path` is the fallback**: offline machine runs lightweight tool GPTQ to produce artifacts (`quant_output/model.safetensors` or `trained_quant_weight.pth`), converter loads it to only do materialize + swap + export (doesn't run GPTQ). The lightweight tool's `opt_main` running GPTQ on this machine's NPU once silently hung (converter one-click integration TODO, see [One-Click Quantization Scheme Selection](#one-click-quantization-scheme-selection)).
4. **One-click quantization (scheme C) implemented**: converter `--quant-method gptq` (`auto_quant.py`: `run_auto_quant` spawns lightweight tool subprocess + swap). w4a16/measured TODO, see [One-Click Quantization Scheme Selection](#one-click-quantization-scheme-selection).
5. **Lightweight tool function oversized**: `swap.py _swap_linear_from_sd` function exceeds 100 lines (221-331), `materialize.py materialize_int4_with_scale` 6 params (exceeds 5-param principle). Both suggested to split by single responsibility + `Int4Spec` dataclass to converge; currently not split.

#### A.1.1 Operator Prototype (quant_batch_matmul_v3_proto.h)

Registered via `REG_OP(QuantBatchMatmulV3)`, defines:

- **Inputs**: `x1`, `x2` (required); `scale`, `offset`, `bias`, `pertoken_scale` (optional)
  - x1/x2 types: int8, int4, hifloat8, float8_e5m2, float8_e4m3fn, float4_e2m1
  - scale types: uint64, float32, int64, bfloat16, float8_e8m0
- **Attributes**:
  - `dtype` (required Int): output type (0=float32, 1=float16, 2=int8, 3=int32, 27=bfloat16)
  - `transpose_x1`/`transpose_x2` (Bool, default false)
  - `group_size` (Int, default 0): 48-bit encoding (k/n/m each 16 bits)
- **Output**: `y` (float16/int8/bfloat16/int32/float32)

The proto comments detail the dtype combinations and quant mode tables supported by each platform (Atlas Inference, A2/A3, Ascend 950).

#### A.1.2 OpSelectFormat (quant_batch_matmul_v3_op_graph.cpp)

Dynamically generates `OpSelectFormat` results (dtype/format combination tables described in JSON) based on whether `x2` is a constant input:

- `listWeightNZ`: x2 is constant (constant folding scenario), weight only retains NZ format
- `listQbmmV3`: non-constant scenario, consistent with the original op info repository

The `QbmmV3OpCheckHelper` constructor selects the list based on `context->IsConstInput("x2")`; `OpSelectFormat` uses a lambda to extract each tensor's dtype/format/unknownshapeFormat lists, assembles into `TensorSpec`, serializes to string via `nlohmann::json`.

Registered to optiling via `IMPL_OP(QuantBatchMatmulV3).OpSelectFormat(QbmmV3OpSelectFormat)`.

#### A.1.3 Host-side Fallback (quant_batch_matmul_v3_fallback.cpp)

When the op can't execute directly on the device side, registers a Host fallback function `QuantBatchMatmulV3ExecuteFunc` via `IMPL_OP(QuantBatchMatmulV3).OpExecuteFunc(...)`, routing to `aclnnQuantMatmulV5` or `aclnnQuantMatmulV4` based on input dtype/shape:

**V5 path**: calls `aclnnQuantMatmulV5` when any of these conditions are met:
- x1 dtype ∈ {FLOAT8_E4M3FN, FLOAT8_E5M2, HIFLOAT8, FLOAT4_E2M1} (v5 input types)
- or "A8W8GB" scenario: x1/x2=int8, y=bf16, pertoken_scale/scale=float32, bias is null or float, and x1 with pertoken_scale, x2 with scale have consistent storage dimension counts

V5 call also reads the `group_size` attribute and passes it in, and pads yScale/x1Offset/yOffset to nullptr.

**V4 path**: otherwise calls `aclnnQuantMatmulV4`.

Attribute indices hardcoded: `transpose_x1=1`, `transpose_x2=2`, `group_size=3`.

#### A.1.4 Transpose Fusion Pass (quant_batch_matmul_v3_transpose_fusion_pass)

**Goal**: delete `Transpose`/`TransposeD`/`Reshape` before `QuantBatchMatmulV3` (and same-type nodes in Bitcast mode), and flip the `transpose_x1`/`transpose_x2` attributes.

Two Pass classes:
- `QuantBatchMatmulV3TransposeFusionPass`: regular pass
- `QuantBatchMatmulV3TransposeLimitFusionPass`: inherits the former, fallbacks in "fusion rules must not be disabled" scenarios, allowing forced fusion when inner axis > 65535 but outer axis ≤ 65535

Main flow:
1. Version check (only effective on GE compiler ≥ 9.1.0)
2. Pre-checks: validate it's a QBMMV3 node, platform capability (supportL12btBf16, supportMmadS8S4), dtype validity, shape dims ≥ 2, whether dynamic shape, whether Bitcast mode
3. Find nodes to delete: based on inner/outer axis relation with 65535, platform l12bt-bf16 support, x2 NZ, decide isDelTransx1/isDelTransx2; extract Transpose nodes on x1/x2; further try to extract equivalent Transpose/Reshape on scale (special equivalence judgment for mx quantization's FLOAT8_E8M0 scale)
4. Execute fusion: flip transpose attributes, bypass Transpose reconnect upstream nodes, report fusion, delete nodes

#### A.1.5 MatMul→QBMMV3 Fusion Pass (z_z_matmul_t_qbmmv3_fusion_pass)

**Goal**: convert `MatMul / MatMulV2 / MatMulV3 / BatchMatMul / BatchMatMulV2 / BatchMatMulV3` to `QuantBatchMatmulV3`, using a constant `scale=1.0` (`0x3F800000`) as "pseudo-quantization" input, to reuse QBMMV3's high-performance impl.

Pattern and construction: `Patterns()` constructs 6 classes of 18 matching patterns for 2/3/4 inputs.

Admission conditions: GE compiler version ≥ 9.0.0; exclude hifloat8; Ascend950 platform also excludes `int8+int8→int32` combination.

Replacement flow: read original node's transpose attributes mapped to QBMMV3's `transpose_x1/transpose_x2`; create constant scale (uint64 1.0, shape={1}); call `QuantBatchMatmulV3(...)` to generate new node; update input/output desc; copy other attributes.

#### A.2.1 Operator Prototype (quant_batch_matmul_v4_proto.h)

Registered via `REG_OP(QuantBatchMatmulV4)`, annotated as "antiquant + matmul fusion operator, supports A8W4 / MxA8W4 / A8W8 / A4W4".

**Inputs (10, 2 required + 8 optional)**:

| Index | name | required | type |
|---|---|---|---|
| 0 | `x1` | yes | float8_e5m2 / float8_e4m3fn / int8 / int4 |
| 1 | `x2` | yes | float4_e2m1 / int4 / int8 |
| 2 | `bias` | no | bfloat16 / float16 / float32 |
| 3 | `x1_scale` | no | float16 / bfloat16 / float8_e8m0 / float32 |
| 4 | `x2_scale` | no | float16 / bfloat16 / float8_e8m0 / uint64 / float32 |
| 5 | `y_scale` | no | uint64 |
| 6 | `x1_offset` | no | float16 / bfloat16 (not supported yet) |
| 7 | `x2_offset` | no | float16 / bfloat16 |
| 8 | `y_offset` | no | float16 / bfloat16 / float32 (not supported yet) |

**Attributes**:
- `dtype` (required Int): output type, only supports 1(float16) and 27(bfloat16)

- `transpose_x2` (Bool, default false): comment says "currently should always be true"

**Key difference from V3**: V4 splits scale into `x1_scale`/`x2_scale`/`y_scale`/`x1_offset`/`x2_offset`/`y_offset`/`x2_table` 8 optional inputs, corresponding to "dequantization + matmul" fusion semantics.

#### A.2.2 V4→V3 Conversion Pass (quant_batch_matmul_v4_to_v3_fusion_pass)

**Goal**: when V4 doesn't need an independent impl on the current platform/scenario, rewrite it to V3.

**Index mapping** (V4_V3_INDEX_MAP):

| V4 input | V4 idx | → | V3 input | V3 idx |
|---|---|---|---|---|
| x1 | 0 | → | x1 | 0 |
| x2 | 1 | → | x2 | 1 |
| bias | 2 | → | bias | 4 |
| x1_scale | 3 | → | pertoken_scale | 5 |
| x2_scale | 4 | → | scale | 2 |
| x2_offset | 7 | → | offset | 3 |

V4's `y_scale / x1_offset / y_offset / x2_table` are dropped when converting to V3.

**Patterns**: constructs 9 patterns (optionalInputNumber from 0 to 8), matching V4 nodes with different actual optional input counts.

**MeetRequirements** — decides whether V4 needs to convert to V3. Two "no conversion needed" conditions; if either is met `return false` (no fusion):

1. **V4 natively supported (MxA8W4)**:
   ```
   x1 == FLOAT8_E4M3FN && (x2 == FLOAT4_E2M1 || x2 == FLOAT) && (y == BF16 || y == FLOAT16)
   ```
   i.e. MxA8W4/MxA8W8FP scenario, V4 itself can run, no downgrade needed.

2. **A8W8 G-B quantization**: when x1/x2 scale both exist, and
   ```
   x1=int8, x2=int8, x1_scale=float32, x2_scale=float32, y=bf16
   && x1 and x1_scale same dim count && x2 and x2_scale same dim count
   ```
   i.e. perblock/pergroup quantization, V4 itself can run.

Otherwise returns true, enters `Replacement` to rewrite V4 to V3.

**Replacement**: uses `EsGraphBuilder` to build new subgraph; traverses `V4_V3_INDEX_MAP`, for each V4 actually-present input creates input ports in order on V3 side; reads V4 attributes (`group_size` -1 → 0); calls `es::QuantBatchMatmulV3(...)` to generate new node; writes back each input desc and output desc per mapping table.

#### A.2.3 V4 Transpose Fusion Pass (quant_batch_matmul_v4_transpose_fusion_pass)

**Goal**: delete `Transpose` / `Reshape` (including dynamic-shape `Pack-Gather-Shape` chain) before `QuantBatchMatmulV4`'s `x2` and `x2_scale` inputs, and flip the `transpose_x2` attribute.

Differences from V3 transpose pass:
- V3 pass handles x1/x2/scale/pertoken_scale four candidates simultaneously; V4 pass **only handles x2 and x2_scale**
- V4 pass only supports `x1=FLOAT8_E4M3FN`, `x2 ∈ {FLOAT4_E2M1, FLOAT}`, `y ∈ {BF16, FLOAT16}` (i.e. MxA8W4 scenario)
- V4 pass additionally handles **dynamic-shape `Reshape(Shape→Gather→Pack)` chain**

### A.3 Overall Relationship Between V4 and V3

| Dimension | V3 op_graph | V4 op_graph |
|---|---|---|
| Operator prototype | scale/offset/pertoken_scale 3 quantization inputs | Split into x1_scale/x2_scale/y_scale/x1_offset/x2_offset/y_offset/x2_table 8 optional |
| OpSelectFormat | yes (two tables by whether weight is constant) | **none** (uses op info repository directly) |
| Fallback | yes, routes to aclnnQuantMatmulV4/V5 | **none** (V4 goes through V4→V3 pass to V3's fallback) |
| Transpose fusion | x1/x2/x2_scale/pertoken_scale four candidates, Bitcast mode, platform l12bt/mmad capability check | only x2/x2_scale two candidates, only MxA8W4 dtype, additionally handles Pack-Gather-Shape dynamic chain |
| MatMul→V3 fusion | yes (z_z_matmul_t_qbmmv3, scale=1.0) | no counterpart |
| V4→V3 conversion | n/a | yes (core pass, decides downgrade by dtype/scenario) |

**Overall design**: V4 is the newer "dequantization+matmul fusion" operator, natively supports MxA8W4/A8W8GB etc. new scenarios; when the scenario exceeds the current platform's V4 impl capability, `QuantBatchMatmulV4ToV3FusionPass` downgrades to V3 to go the old path.

**Mutual exclusivity of the two V4 passes**: `QuantBatchMatmulV4TransposeFusionPass`'s valid dtype exactly equals to_v3 pass's `isV4Supported` condition. Satisfies MxA8W4 → transpose fusion pass takes effect, to_v3 pass doesn't; doesn't satisfy MxA8W4 and not A8W8GB → to_v3 pass takes effect, transpose fusion pass doesn't.

### A.4 MxA8W4 and A8W8GB Scenario Details

These two names are abbreviations for quantization scenarios, the rule is `<scale-mode>A<xbits>W<ybits>`:

- **A8 / W4 / W8**: Activation is 8-bit, Weight is 4-bit or 8-bit. The "8/4" here refers to data bit-width, not limited to int or float — float8_e4m3fn counts as 8-bit, float4_e2m1 counts as 4-bit.
- **Mx prefix**: Microscaling quantization mode, uses low-bit float (float8/float4) for activation and weight, float8_e8m0 for scale, scale groups 32 elements along k axis (corresponds to V3 proto's `mx quant` table, group_size `[1,1,32]`).
- **GB suffix**: Group-Block, i.e. pergroup-perblock or perblock-perblock quantization (V3 proto's group_size `[1,128,128]` / `[128,128,128]`). Unlike perchannel/pertensor (scale is 1D), GB mode scale shape has same dims as data.

| Scenario | x1 | x2 | scale | output |
|---|---|---|---|---|
| MxA8W4 | float8_e4m3fn (8b float) | float4_e2m1 (4b float) | x1_scale/x2_scale usually float8_e8m0 | bf16/fp16 |
| A8W8GB | int8 | int8 | float32 (same dims as x1/x2) | bf16 |

**A8W8GB judgment key**: scale's dim count must be same as data's.
- perchannel/pertensor: scale is 1D (e.g. `(n,)`), doesn't match x2's 2D → not GB
- perblock/pergroup: scale is 2D (e.g. `(ceil(k/128), ceil(n/128))`), same 2D as x2 → hits GB

**Complete path**:

| Scenario | graph op | final opapi |
|---|---|---|
| MxA8W4 / A8W8GB | **retain V4** (no fusion) | V4's own tiling/kernel |
| other scenarios | V4 → V3 (to_v3 pass) | V3 fallback → `aclnnQuantMatmulV4` (most cases) |

### A.5 V3's perchannel Quantization Support

V3 supports perchannel quantization. The proto explicitly lists two quantization modes containing perchannel (for Ascend 950):

The naming rule is `<x1-side>-<x2-side>`, corresponding to proto's x1 uses `pertoken_scale`, x2 uses `scale`:
- `pertensor-perchannel`: x1=pertensor (or null), x2=perchannel
- `pertoken-perchannel`: x1=pertoken, x2=perchannel

**scale shape for perchannel** (`quant_batch_matmul_v3_proto.h:59-62`, external dependency CANN 9.2.0):
```
When the quant mode of x2 is perchannel or pertensor, the shape is 1D (t,),
with t equal to 1 or n, where n is the same as that of x2.
```
- `t = n`: true perchannel (one scale per channel)
- `t = 1`: actually pertensor

**Relationship with V4**: V4's A8W8GB judgment (`quant_batch_matmul_v4_to_v3_fusion_pass.cpp:127-128`, external dependency CANN 9.2.0) requires scale dim count same as data, which **excludes perchannel** — because perchannel scale is 1D, while x2 is 2D/3D, dim counts differ. So A8W8's perchannel/pertensor scenarios, V4 is converted to V3 to execute.

| A8W8 quantization mode | scale shape | V4 handling |
|---|---|---|
| pertensor | 1D, t=1 | V4→V3 conversion (goes V3 path) |
| perchannel | 1D, t=n | V4→V3 conversion (goes V3 path) |
| perblock/pergroup | 2D/3D (same dims) | retain V4 (A8W8GB) |

### A.6 pertoken / pergroup / perchannel / perblock Concepts

In one sentence: **these "per-X" answer "how many elements share one scale (scaling factor)". Granularity from coarse to fine.**

Assume activation matrix x1 shape is `(m, k)` (m rows k cols), weight matrix x2 shape is `(n, k)`.

```
pertensor  —— the whole matrix shares 1 scale
┌────────────────────┐
│  all use S0         │   → 1 scale
└────────────────────┘

pertoken   —— one scale per row (per token)
┌────────────────────┐
│  S0 S0 S0 S0 S0 S0 S0 S0 │  ← row 0 uses S0
│  S1 S1 S1 S1 S1 S1 S1 S1 │  ← row 1 uses S1
│  S2 S2 S2 S2 S2 S2 S2 S2 │
│  S3 S3 S3 S3 S3 S3 S3 S3 │
└────────────────────┘   → m scales

perchannel —— one scale per column (per output channel)
┌────────────────────┐
│ S0 S1 S2 S3 S4 S5 S6 S7│  ← col 0 uses S0, col 1 uses S1...
│ S0 S1 S2 S3 S4 S5 S6 S7│
│ S0 S1 S2 S3 S4 S5 S6 S7│
│ S0 S1 S2 S3 S4 S5 S6 S7│
└────────────────────┘   → k scales (or n, depending on who's the "channel")

pergroup   —— one scale per consecutive group_size (e.g. 128) elements along an axis
┌────────────────────┐
│ S0 S0 S0 S0 S1 S1 S1 S1│  ← every 4 a group (illustrative, actually 128)
│ S2 S2 S2 S2 S3 S3 S3 S3│
│ S4 S4 S4 S4 S5 S5 S5 S5│
│ S6 S6 S6 S6 S7 S7 S7 S7│
└────────────────────┘   → m × ceil(k/group) scales

perblock   —— cut into 2D blocks, one scale per block
┌───────┬───────┐
│  S0   │  S1   │   ← top-left 4×4 block uses S0, top-right 4×4 block uses S1
├───────┼───────┤
│  S2   │  S3   │
└───────┴───────┘   → ceil(m/gs) × ceil(k/gs) scales
```

| Mode | Who shares one scale | scale count | granularity |
|---|---|---|---|
| **pertensor** | the whole tensor | 1 | coarsest |
| **perchannel** | same channel (a whole col/row) | n or k | medium |
| **pertoken** | same row (same token) | m | medium |
| **perblock** | a 2D block (e.g. 128×128) | ceil(m/128)×ceil(k/128) | finer |
| **pergroup** | a consecutive 1D segment along an axis (e.g. every 128) | m×ceil(k/128) | finest |

**In V3 who uses which**:
- **x1 (activation)** uses `pertoken_scale`: optional pertoken / pertensor / perblock / pergroup
- **x2 (weight)** uses `scale`: optional perchannel / pertensor / perblock

V3 weight side has no "pergroup" mode — the finest is **perblock** (groups by both K and N axes). If you only want to group along K axis, not N axis, V3 has no ready-made mode support.

### A.7 pergroup Judgment Mechanism

pergroup is judged by **two things combined**: the scale tensor's **shape** + the op's **group_size attribute**. There's no explicit "quant_mode" enum field.

#### Judgment basis 1: pertoken_scale's shape

Compare the four modes' pertoken_scale shapes for x1 (activation) side (`quant_batch_matmul_v3_proto.h:77-83`, external dependency CANN 9.2.0):

| Mode | pertoken_scale shape | key feature |
|---|---|---|
| pertensor | 1D `(1,)` | only one value |
| pertoken | 1D `(m,)` | one value per row |
| **pergroup** | 3D `(batch, m, ceil(k/128))` | **m is full, k is grouped** |
| perblock | 3D `(batch, ceil(m/128), ceil(k/128))` | both m and k grouped |

The **only shape difference** between pergroup and perblock:

```
pergroup :  (batch, m          , ceil(k/128))   ← m not divided by 128
perblock :  (batch, ceil(m/128), ceil(k/128))   ← m also divided by 128
```

#### Judgment basis 2: group_size attribute

`group_size` is a 48-bit encoded int attribute (`quant_batch_matmul_v3_proto.h:93-105`, external dependency CANN 9.2.0):

```
bits  0-15  → group_size_k   (group size along K axis)
bits 16-31  → group_size_n   (group size along N axis)
bits 32-47  → group_size_m   (group size along M axis)
```

pergroup vs perblock is determined by **group_size_m**:

| group_size_m | meaning | x1 mode |
|---|---|---|
| **1** | M axis not grouped (1 m per group → equivalent to no grouping) | **pergroup** |
| **128** | M axis every 128 a group | perblock |

The support table (`:231-243`) also confirms:

```
pergroup-perblock : [group_size_m, group_size_n, group_size_k] = [1,   128, 128]
perblock-perblock : [group_size_m, group_size_n, group_size_k] = [128, 128, 128]
```

Both x2 side are perblock (n=128, k=128), **the only difference is group_size_m being 1 or 128**.

#### Judgment basis 3: dtype restriction

pergroup-perblock mode also requires specific dtype (`:212-218`):

```
| x1                       | x2                       | pertoken_scale | scale  |
| float8_e4m3fn/float8_e5m2 | float8_e4m3fn/float8_e5m2 | float32        | float32 |
| hifloat8                  | hifloat8                 | float32        | float32 |
```

#### Summary: how pergroup is "spotted"

When the graph compiler sees a V3 node, it judges whether x1 is pergroup via this combination:

```
pertoken_scale is 3D && 2nd dim == m (full, not divided by 128) && 3rd dim == ceil(k/128)
    && group_size attribute decodes group_size_m == 1
    && dtype ∈ {float8_e4m3fn, float8_e5m2, hifloat8} + float32 scale
        → judged as pergroup
```

No single field directly says "pergroup"; all inferred jointly by **shape structure + group_size encoding + dtype**.

### A.8 W4A8 pergroup + pertoken Scenario Feasibility Analysis

If weight uses W4A8 pergroup quantization and activation uses pertoken quantization, the following key points need clarification:

#### Problem 1: "pergroup for weight" is not an independent mode in V3

V3 only supports three quantization modes for x2 (weight) side:
- pertensor: scale 1D `(1,)`
- perchannel: scale 1D `(n,)`
- perblock: scale `(batch, ceil(k/128), ceil(n/128))`

And "pergroup" in V3 is an **x1 (activation) side** mode. "weight pergroup (every 128 along K axis)" is closest to x2's **perblock** (but perblock groups by both K and N). V3 doesn't support x2 quantization that only groups by K, not by N.

#### Problem 2: int8/int4 (W4A8) dtype combination not supported

In V3 and V4 support tables, x1 and x2 dtype must **be paired same**:

| Platform | int8 row | int4 row |
|---|---|---|
| A2/A3 | int8/int8 | int4/int4 |
| 950 | int8/int8 | no int4 |

**There's no int8/int4 row**. Although V4 registers `x1=DT_INT8` and `x2=DT_INT4`, the proto comment says A8W4 scenario's x2 is `float4_e2m1` (float4), not int4; int4 only appears in A4W4 (int4/int4).

#### Viable Alternative Schemes

| Scheme | x1 dtype | x2 dtype | quantization mode | platform | notes |
|---|---|---|---|---|---|
| A. MxA8W4 (V4 native) | float8_e4m3fn | float4_e2m1 | Mx (float8_e8m0 scale) | 950 | x1_scale/x2_scale is float8_e8m0, group_size [1,1,32] |
| B. A4W4 pertoken-perchannel (V3) | int4 | int4 | pertoken + perchannel | A2/A3 | x1 must also be int4, scale 1D |
| C. int8/int4 pergroup | — | — | — | — | **currently neither V3 nor V4 supports** |

> **Note**: this project early selected path C' (V4 integer int4 per-group); measured CANN 9.2.0 pre-compiled kernel dir contains `QuantBatchMatmulV4_ND_ND_int8_int4_{bf16,fp16}` (tilingKey=24), i.e. V4 runtime kernel covers the integer int8/int4 combination. The proto's REG_OP dtype list and runtime kernel coverage aren't fully consistent; proto only lists the mxfp branch but runtime kernel covers integer dtype. But measured eager path `npu_quant_matmul` int8/int4 results wrong, finally switched to scheme A in-house op.
